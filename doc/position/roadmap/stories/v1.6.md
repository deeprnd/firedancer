# V1.6: Guarded Broker, Payment, And Crypto Sandbox

**Status: Later · Milestone: M5**

Connect sandbox broker, payment, bank, or crypto accounts and submit approved
small actions through the same safe-action flow.

---

## Product Intent

V1.6 adds signed action envelopes, sandbox adapters, read-back reconciliation,
and a kill switch. Paper mode remains the default.

## User Story

As a product evaluator, I can connect sandbox broker, payment, bank, or crypto
accounts and submit approved small actions through the same safe-action flow.

## Tasks

- V1.6.T1: Define sandbox adapter manifests for broker, payment processor,
  bank transfer, and crypto custody or wallet connectors.
- V1.6.T2: Add paper/sandbox/live mode switch with safe default to paper or
  draft-only mode.
- V1.6.T3: Add signed action envelope for approved sandbox orders, payment
  retries, transfers, and crypto withdrawals.
- V1.6.T4: Add deterministic action id and idempotency key.
- V1.6.T5: Submit sandbox actions only after capability, evidence, limit, and
  approval checks pass.
- V1.6.T6: Read back downstream status and reconcile it with the local
  proposal.
- V1.6.T7: Create mismatch note or reconciliation case when read-back differs.
- V1.6.T8: Add kill switch that blocks all sensitive execution capabilities.
- V1.6.T9: Add tests for duplicate action id, stale approval, revoked approval,
  out-of-scope destination, read-back mismatch, and kill-switch behavior.
- V1.6.T10: Add an authenticated financial event ingestion endpoint via `tkapi`:
  `POST /v1/events` accepts external events with source identity, idempotency
  key, event type, payload, timestamp, and source signature. The endpoint
  validates transport shape and authenticates the source before forwarding to
  `tkings`. No event reaches `tkings` without a recognized source identity and
  valid signature.
- V1.6.T11: Return one of four explicit responses for each ingested event:
  accepted (stable event id and sequence number), duplicate (idempotency key
  already seen, returns original event id with no reprocessing), malformed
  (shape or encoding invalid, no state change), or rejected (source identity
  not recognized or signature invalid, no state change). Malformed and rejected
  responses disclose no internal state beyond the response code.
- V1.6.T12: Add source identity registration: each external event source has a
  configured source id, allowed event types, allowed rate limits, and a public
  key or token for signature verification. Unregistered sources are rejected
  before any payload parsing.
- V1.6.T13: Scope idempotency key uniqueness per source identity and time
  window. A duplicate within the window returns the original accepted response
  without reprocessing or altering any business state.
- V1.6.T14: Add integration tests for accepted event, duplicate event (same
  idempotency key within window), malformed payload, unregistered source,
  invalid or expired signature, and rate-limit-exceeded rejection.

Acceptance:

- Small eligible actions can be submitted to sandbox connectors only after
  policy, evidence, approval, signed envelope, and action-id checks pass.
- Read-back confirms status or creates a mismatch artifact.
- An external event with a known source identity and valid signature is accepted
  with a stable event id and sequence number.
- A duplicate idempotency key within the window returns the original event id
  without reprocessing.
- A malformed payload, unregistered source, or invalid signature is rejected
  with no state change and no internal state disclosed.

## Non-Goals

- no production live execution by default
- no margin
- no derivatives
- no autonomous execution

## Evidence Gate

- Sandbox adapter behavior is substitutable by replay capsules.
- A read-back mismatch is demonstrated and produces a reconciliation artifact.
