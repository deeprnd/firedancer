# V1.11: Investment Demo Release Closure

**Status: Next · Milestone: M1**

Turn the useful V1.1 engineering demo into a defensible investment-paper-trade
release. Preserve the deterministic fixture flow, but close the gaps between
direct function tests and the governed Tickoni product path.

---

## Product Intent

Starting point: the offline USD 2,000 fixture demo builds a basket, ticket,
paper fill, and replay-match result. USD 25,000 and restricted `SOXL` flows are
covered by deterministic tests. Thesis, catalog, basket, portfolio, buy/sell,
market/limit, model, adapter, audit, and replay scaffolding exists. Unit and
local-mock integration lanes are deterministic.

Release findings carried from V1.1:

1. Bind paper placement to a validated ticket, exact proposal hash, capability
   envelope, policy decision, account, environment, and deterministic action id.
2. Run the investment demo through governed boundaries: `tkcase`, `tkdisp`,
   `tkagnt`, `tkmodl`, `tktool`, `tkadpt`, `tkaudt`, `tkrepl`.
3. Replace narrow CLI parser with bounded structured intent extraction.
4. Complete the documented V1.1 trade checks with exact denied reasons.
5. Complete ticket and paper-result contracts, including save-as-proposal.
6. Make replay source-driven and fail-closed.
7. Finish `tkmodl` governance.
8. Put audit, metrics, diagnostics in the executable demo path.
9. Reconcile roadmap, WBS, integration-test specs, demo commands, release
   status.
10. Replace in-process tile-thread spike with supervisor-managed tile processes
    over Firedancer shared-memory links.

## User Story

Same as V1.1, but now every step runs through governed boundaries with full
audit, replay, and no-bypass enforcement.

## Success Demo

One offline command shows, in order:

- plain-English AI-infrastructure thesis normalized into bounded intent
- explainable basket and rejected candidates
- affordability and the USD 2,000 allowed ticket and paper fill
- USD 25,000 denial with exact limit and effective maximum
- direct `SOXL` denial before quote or paper-fill work
- direct-placement bypass denial
- audit, metrics, and diagnostic artifact locations
- replay success from captured substitutions
- deliberate tamper detection with first divergent field and sequence

## Release Gate

- `just test-unit-tk` passes with no unexpected skips
- `just test-integration-tk` passes offline against local mocks
- one deterministic `just demo-tk` prints all required scenarios and produces
  the proof bundle
- explicit live-local-model smoke lane remains opt-in and uses `tkmodl`
- no paper action can bypass validated ticket, policy, capability, action identity
- replay performs no live model, broker, market, trading, payment, or execution
  effects
- V1.11 topology runs tiles as processes over Firedancer shared-memory links
- all V1.11 release findings have executable evidence or are explicitly de-scoped

## Non-Goals

- no live brokerage order placement
- no margin, options, futures, leveraged or inverse ETF execution
- no production market-data dependency
- no autonomous trading or portfolio rebalancing
- no broad UI, partner API, or sandbox connector expansion beyond the governed
  paper-trade loop

### V1.11.S2: Tkmodl governed boundary

Tasks:

- V1.11.S2.T1: Keep provider-wire transport types private and distinct from the
  governed `tkmodl` boundary contract.
- V1.11.S2.T2: Add validated `TkModlRequest` with identity, scope, actor, role,
  workflow, account, capability, model, budget, limits, replay fields.
- V1.11.S2.T3: Add `TkModlConfig` with provider enablement, model allowlist,
  endpoint mapping, hard timeouts, hard limits, per-request and per-run budgets.
- V1.11.S2.T4: Add pure validator with stable decision codes for live allow,
  replay allow, and fail-closed denials.
- V1.11.S2.T5: Build provider requests only from validated `tkmodl` decisions;
  emit audit fields for policy version, budget, model, hashes, token usage,
  retry, latency, replay.
- V1.11.S2.T6: Add per-run, per-role, and per-case model-call limits to
  `TkModlConfig` as enforced counters. When a per-role or per-case limit is
  reached, the request is denied with a call-limit-exceeded audit record before
  any provider dispatch.
- V1.11.S2.T7: Define call-limit-exceeded as an auditable terminal state: emit
  an audit record with budget id, limit type (run, role, or case), consumed
  call count, configured limit, run id, and policy version. Not a runtime error.
- V1.11.S2.T8: Define budget-exhaustion stop state: when the token budget is
  exhausted, the run transitions to budget-exhausted and emits an audit record
  with budget id, consumed tokens, token limit, run id, and policy version
  before halting. Budget exhaustion is an expected terminal state and a
  policy-relevant event.

Acceptance:

- No model call in the investment flow can bypass `tkmodl`.
- Unknown model ids, disabled providers, and oversize requests fail closed.
- Replay can substitute captured model output without invoking a live provider.
- An unconfigured GPU provider falls back to stub without a silent model call
  attempt.
- A per-role model-call limit produces a call-limit-exceeded audit record and
  halts that role's model access without affecting other roles or the run.
- Budget exhaustion produces an audit record with budget id, consumed tokens,
  and token limit before the run halts; the run does not continue even if the
  model would respond.

### V1.11.S4: Source-driven replay and proof bundle

Tasks:

- V1.11.S4.T1: Reconstruct the investment flow from captured thesis/run inputs.
- V1.11.S4.T2: Route model replay through `tkmodl` substitution; adapter replay
  through captured substitutions.
- V1.11.S4.T3: Reject missing/mismatched substitutions fail-closed.
- V1.11.S4.T4: Emit audit, metrics, diagnostics artifacts for all event types.
- V1.11.S4.T5: One `just demo-tk` command shows allowed, blocked, restricted,
  bypass, replay, and tamper.
- V1.11.S4.T6: Define a content-addressed evidence store for the V1.11
  investment flow: each evidence item has a canonical content hash computed
  from its type and payload, a stable item id, source identity, and sequence
  number. The same content always maps to the same hash regardless of when it
  was captured.
- V1.11.S4.T7: Build ordered event-hash references into the replay capsule:
  each captured event carries its source event sequence number and event content
  hash. The capsule is invalid if any hash is missing or the sequence is
  non-monotonic.
- V1.11.S4.T8: Add agent role, transcript hash, and tool-call hash references
  to the replay capsule. The transcript hash covers the ordered sequence of
  model requests and responses for the run. The tool-call hash covers the
  ordered sequence of tool requests and adapter results. Each adapter result is
  stored as a content-addressed item with adapter id, invocation sequence
  number, and output hash.
- V1.11.S4.T9: Add expected replay outcome to the capsule: final policy state,
  proposed action when present, and expected policy result. Replay fails closed
  if the reconstructed outcome does not match the expected outcome field.

Acceptance:

- Replay performs no live effects.
- Deliberate tamper produces a first-divergence report.
- Demo artifacts expose audit, metrics, diagnostics, replay locations.
- Content-addressed evidence items produce the same hash for identical content
  regardless of capture time.
- Replay capsule event-hash sequence is monotonic; a non-monotonic or missing
  hash is rejected before any replay run begins.
- A reconstructed outcome that differs from the expected outcome field causes
  replay to fail closed with a divergence record.

### V1.11.S7: Bounded agent run envelope

Tasks:

- V1.11.S7.T1: Define an agent run envelope with run id, agent identity, role,
  workflow, case or synthetic run id, policy version, capability envelope id,
  step limit, retry limit, token budget id, start time, and run state.
- V1.11.S7.T2: Define run state as a tagged union or enum: running, completed,
  step-limit-exceeded, retry-limit-exceeded, budget-exhausted, policy-denied,
  and error. Budget-exhausted and step-limit-exceeded are expected terminal
  states, not runtime errors.
- V1.11.S7.T3: Add a loop step counter: each iteration of an agent reasoning
  loop increments the step counter. When the step limit is reached the run
  transitions to step-limit-exceeded and emits an audit record before halting.
- V1.11.S7.T4: Add a retry counter: each agent-level retry increments the
  counter independently of any model-level retry. When the retry limit is
  reached the run transitions to retry-limit-exceeded.
- V1.11.S7.T5: Audit budget-exhaustion as a policy-relevant event: emit an
  audit record with budget type, budget id, consumed tokens, token limit, run
  id, and policy version before halting.
- V1.11.S7.T6: Require agents to carry explicit role and identity context on
  every model request, tool request, and adapter request they generate. The
  run envelope is the sole authority for this context; an agent may not
  substitute a different identity or role on any downstream request.
- V1.11.S7.T7: Add tests for step-limit-exceeded halt with audit record,
  retry-limit-exceeded halt, budget-exhaustion audit record, and a run that
  completes within all limits.

Acceptance:

- A step-limit-exceeded run emits an audit record and halts without a runtime
  error or unhandled panic.
- Budget exhaustion produces an audit record with budget id, consumed tokens,
  and token limit before the run halts.
- An agent run that exhausts its budget cannot continue even if the model would
  respond to further requests.

### V1.11.S8: Tool broker and MCP-compatible dispatch

Tasks:

- V1.11.S8.T1: Define a tool request schema at the `tktool` boundary: tool
  request id, tool name, invocation protocol, actor id, role, workflow, case
  or synthetic run id, policy version, capability envelope id, and input hash.
- V1.11.S8.T2: Define invocation protocol as an enum: model-native-function-call
  and mcp-tool-call. Model-native function calls from a model response are
  normalized into the same tool request schema as MCP-style requests before any
  adapter dispatch.
- V1.11.S8.T3: Validate the tool request at the `tktool` boundary: tool name
  must be in the configured allowed tool registry, invocation protocol must be
  recognized, and capability envelope must be present and non-empty. Invalid
  requests fail closed before any adapter dispatch.
- V1.11.S8.T4: Dispatch normalized tool requests to `tkadpt` only. Agents and
  model output must not reach `tkadpt` directly; `tktool` is the only permitted
  dispatch path.
- V1.11.S8.T5: Emit tool request audit fields: request id, tool name,
  invocation protocol, adapter id, input hash, output hash, latency, result
  status, and replay substitution id when applicable.
- V1.11.S8.T6: Add tests for model-native function call normalization, MCP-style
  request normalization, unknown tool name rejection, missing capability envelope
  rejection, direct adapter call rejection, and replay substitution.

Acceptance:

- A model-native function call and an MCP-style request for the same tool
  produce identical normalized tool requests at the `tktool` boundary.
- An unknown tool name or missing capability envelope is rejected before any
  adapter dispatch.
- Agents and model output cannot reach `tkadpt` except through `tktool`.
