# V1.13: Non-Investment Operations Workflows

**Status: Later · Milestone: M3**

Open the Tickoni consumer-finance harness to operations teams — payment
exceptions, reconciliation breaks, fraud and risk triage, and compliance case
preparation — through the same governed agent-plus-approval pattern that governs
consumer money decisions, with a CaseOps board as the operator-facing surface.

---

## Product Intent

V1.2 proved the consumer-facing payment guard: a consumer reviews a failed
payout, Tickoni checks the beneficiary and rail, and proposes a safe retry or
escalation. V1.13 targets the operations tier behind that consumer experience.
A fraud analyst works a velocity spike. A reconciliation analyst resolves a
processor batch mismatch. A compliance officer prepares an AML escalation
packet. All use the same Tickoni harness: event ingested, case created, policy
assigns capabilities, agent investigates through the governed tool broker, audit
records everything, draft-only action proposed, human approves, downstream
response sent only after approval, and replay capsule generated.

CaseOps is the operator UI surface. TigerBeetle is the authoritative ledger for
balances, transfers, fills, and accounting state — accessible to agents only
through `tkadpt` reads and to approved mutations only through `tkexec` with
policy, signed envelope, and human approval.

## User Story

As a payment operations analyst, reconciliation analyst, fraud investigator, or
compliance officer, I can open a case in CaseOps, let a governed agent
investigate using approved read tools, review the agent's evidence and draft
proposal, and approve or reject the proposed action — all with a full audit
trail and deterministic replay.

Example — fraud analyst:

```text
Velocity spike: 47 transactions in 6 minutes on merchant_xyz, exceeding the
configured 10-per-minute threshold. Device cluster matches 3 prior chargebacks.
```

Tickoni answers:

```text
Merchant: merchant_xyz
Signal type: velocity spike + device cluster
Cluster match: 3 prior chargebacks (chargeback_ids: ...)
Proposed: hold on new authorizations pending review
Execution requires approval.
Agent findings: [evidence packet]
```

## What The Operator Can Do

- view the case queue filtered by workflow type, priority, age, analyst, and
  status
- open a case and see the source event, normalized facts, prior case history,
  and linked evidence
- review agent investigation findings, tool calls, model output, and evidence
  references
- see the policy decision and capability envelope for each proposed action
- approve, reject, or escalate a draft proposal
- view the audit timeline and replay status for any case
- replay a case from captured inputs to verify the agent's findings under
  changed policy or fixture conditions
- export a case record for partner, regulator, or internal audit review

## What The Operator Sees

- case queue with workflow type badge, priority, age, assigned analyst, and
  status
- case detail: source event summary, normalized event facts, linked cases,
  evidence packet, agent findings, model usage, tool calls, policy decision,
  approval state, audit timeline, replay status
- draft-only outputs: merchant response, investigator note, correction proposal,
  hold or review proposal, escalation packet, compliance case narrative,
  missing-document classification, and audit packet
- approval workflow: pending proposals with proposal hash, capability envelope,
  evidence summary, expiry, and maker-checker requirement where applicable
- replay panel: capsule id, expected outcome, divergence report when present

## Non-Goals

- no autonomous fraud holds or account freezes without approval
- no autonomous compliance decisions (SAR filing, sanctions action, payout
  approval) without approval
- no direct TigerBeetle write access from agents, CaseOps UI, or `tkapi`
- no direct payment, crypto, risk, or compliance adapter execution without the
  approved `tkexec` path
- no generic CRM or ticketing system replacement
- not the consumer-facing payment-retry flow (that is V1.2)
- not the first consumer-money product path

## WBS

### V1.13.S1: CaseOps operations board

Tasks:

- V1.13.S1.T1: Define the CaseOps case record schema: case id, workflow type,
  source event id, source event type, normalized event summary, priority tier,
  assigned analyst id, assigned analyst role, status, created_at, updated_at,
  linked case ids, evidence item ids, proposal id when present, approval state,
  and replay capsule id.
- V1.13.S1.T2: Define case status as an enum: open, investigating,
  pending-approval, approved, rejected, escalated, audited, and closed. Status
  transitions are append-only audit events; no status can be silently overwritten.
- V1.13.S1.T3: Define the case queue view: paginated list filterable by workflow
  type (payment-exception, reconciliation-break, fraud-risk, compliance), status,
  priority, analyst, and age bracket. Queue ordering is deterministic given the
  same filter set.
- V1.13.S1.T4: Define the case detail view: source event, normalized facts,
  evidence packet, agent findings, model usage summary, tool call summary, policy
  decision, capability envelope id, approval state, audit timeline link, replay
  status link, and draft proposal when present.
- V1.13.S1.T5: Define role-based access: analyst may investigate and propose but
  not approve their own proposals; reviewer may approve, reject, or escalate;
  compliance officer has read access to compliance workflow cases; supervisor has
  read access to all workflow types. Access is governed by the capability envelope
  for each case action, not by UI gating alone.
- V1.13.S1.T6: Add case assignment and routing: cases are assigned to analysts
  by workflow type and role. Routing is deterministic given the same assignment
  policy; it does not depend on analyst availability state or queue depth alone.
- V1.13.S1.T7: Add tests for status transition audit records, unauthorized
  approval attempt rejection, cross-workflow access control, deterministic queue
  ordering, and case detail completeness.

Acceptance:

- Every case status transition produces an audit record; no status change is
  silent.
- An analyst cannot approve their own proposal; the attempt is rejected with an
  explicit policy denial.
- Queue ordering is reproducible from the same filter parameters and case state.

### V1.13.S2: Payment exception workflow

- V1.13.S2.T1: Define the payment exception event set: `payment_failed`,
  `settlement_delayed`, `payout_blocked`, `authorization_declined`,
  `processor_timeout`, `refund_failed`, `capture_failed`, `batch_mismatch`,
  and `unmatched_refund`. Each event type has a defined normalized schema with
  processor id, merchant id, amount, currency, rail, beneficiary or recipient
  id, failure code, failure reason, retry count, and timestamp.
- V1.13.S2.T2: Define operations-level payment exception capabilities: beyond
  V1.2's consumer retry proposal, add `batch_payment.investigate`,
  `capture_failure.classify`, `refund_failure.classify`,
  `processor_record.reconcile`, and `merchant_response.draft`. These are
  investigate and draft capabilities; execution requires approval.
- V1.13.S2.T3: Define the payment exception evidence packet: source event,
  processor record, batch record where applicable, beneficiary check, rail and
  currency check, retry state, risk flags, merchant history, and linked prior
  exception cases.
- V1.13.S2.T4: Add deterministic processor, batch, beneficiary, and merchant
  history fixtures for each exception event type.
- V1.13.S2.T5: Add draft merchant response and internal investigator note
  outputs. Both are review-only and non-executing; neither reaches a processor
  or customer without explicit operator approval.
- V1.13.S2.T6: Add correction proposal path: for capture failures, unmatched
  refunds, and batch mismatches, a correction proposal carries the corrected
  amount, action type, and evidence hash; execution requires `tkexec` with
  approval.
- V1.13.S2.T7: Add tests for each exception event type, draft output
  non-execution, correction proposal approval requirement, and replay from
  captured processor fixtures.

Acceptance:

- Each exception event type produces a normalized case with a complete evidence
  packet.
- Draft merchant responses and investigator notes are non-executing by
  construction; they cannot reach a processor without the approved execution
  path.
- A correction proposal requires `tkexec` approval; a direct correction attempt
  is denied.

- Each break event type produces a normalized evidence packet with discrepancy

- V1.13.S4.T5: Define the hold or review proposal: affected entity, proposed

- V1.13.S4.T6: Define the investigator note output: review-only free-text draft

- The investigator note is review-only by construction; it cannot trigger a
  processor action without the approved execution path.
- Each fraud signal produces a triage evidence packet with contributing event ids
  and risk tier at detection time.

  merchant_response, investigator_note, correction_proposal, hold_proposal,

  missing_document_classification, and audit_packet. An output of any type
  other than this enum is rejected.
- V1.13.S7.T3: Enforce draft-only invariant: no operator output type can trigger
  processor, bank, exchange, sanctions, regulatory, or ledger action without
  transitioning through a proposal, approval, and `tkexec` path. Draft outputs
  are anchored to a case id, proposal id, evidence hash, and analyst identity.
- V1.13.S7.T4: Add approval requirement rules per output type: correction
  proposals and hold proposals require maker-checker approval; escalation packets
  require compliance officer sign-off; audit packets are read-only exports
  requiring no approval.
- V1.13.S7.T5: Add output schema definitions for each draft output type. Fields
  must include case id, output type, analyst identity, evidence hash, policy
  version, created_at, and status (draft, pending-approval, approved, rejected).
- V1.13.S7.T6: Add tests for each output type's draft-only enforcement, approval
  requirement by type, unauthorized execution attempt denial, and output schema
  completeness.

Acceptance:

- A correction proposal or hold proposal that bypasses the approval step is
  denied; the draft status alone does not grant execution authority.
- An audit packet is a read-only export that requires no approval; it contains
  no mutable state.
- Each draft output type anchors to a case id, evidence hash, and analyst
  identity; an output missing any anchor field is rejected.

Tasks:

- V1.13.S8.T1: Define the accounting ledger adapter manifest for TigerBeetle:
  read-only balance reads and transfer reads routed through `tkadpt`. Agents,

- V1.13.S8.T2: Define the ledger correction proposal as an `tkexec`-gated

  `tkexec` will accept it.
- V1.13.S8.T3: Define read-back reconciliation for approved ledger corrections:
  after `tkexec` posts the correction entry, read back the resulting balance and
  transfer record and compare against the expected state in the proposal. A
  mismatch creates a reconciliation break case.
- V1.13.S8.T4: Add deterministic TigerBeetle balance and transfer fixtures for
  the reconciliation-break and payment-exception workflows.
- V1.13.S8.T5: Add tests proving agents cannot call TigerBeetle directly,
  correction proposals require `tkexec` approval, read-back mismatch creates a
  break case, and fixture-backed ledger reads produce deterministic results.

Acceptance:

- A direct TigerBeetle call from an agent, UI, or `tkapi` handler is denied at
  the adapter boundary.
- A ledger correction attempt without `tkexec` approval is denied by policy.
- A read-back mismatch after an approved correction is audited and creates a new
  reconciliation break case.

## Evidence Gate

- Each of the four non-investment workflow types (payment-exception,
  reconciliation-break, fraud-risk, compliance) has a deterministic demo command
  and at least three event fixtures (clear, flagged, edge-case) per event type.
- Draft outputs are non-executing by construction; a bypass attempt is denied
  before any processor, bank, ledger, or compliance action.
- Agents cannot call TigerBeetle directly; ledger reads are routed through
  `tkadpt` and writes through `tkexec` with approval.
- Replay runs with no live model, processor, bank, risk, compliance, or ledger
  effects; deliberate divergence produces a first-divergence report.
- Every case status transition produces an audit record; no transition is silent.
