# V1.1.S6 Lean Demo Extension

## Goal

Finish a lean working V1.1 e2e demo instead of a broad half-built surface.

The demo should prove one money-decision loop end to end:

```text
investment thesis
  -> basket
  -> policy decision
  -> trade ticket
  -> paper fill fixture
  -> audit chain
  -> replay
```

The default lane must be deterministic and offline. Live llama.cpp is useful as
a smoke test, but it is not the default proof path.

## Scenario 1: AI Infrastructure Allowed Trade

Input:

```text
Invest USD 2,000 in AI infrastructure for brokerage.demo_ops.
Use US-listed ETFs and large-cap equities.
Avoid leveraged/inverse products and keep single-name weight <= 25%.
```

Expected output:

- thesis summary,
- basket with eligible AI infrastructure instruments,
- rejected restricted instruments such as `SOXL` and `BULZ`,
- market paper ticket,
- affordability result `allow`,
- paper fill fixture,
- audit chain records,
- replay success.

Required demo facts:

- account: `brokerage.demo_ops`,
- notional: USD 2,000,
- market: US,
- venues: NYSE and NASDAQ,
- asset classes: equity and ETF,
- mode: paper,
- capability: `trading_order.propose` followed by paper
  `trading_order.place`.

Why this is the primary demo:

It proves the whole money-decision loop in the smallest useful form. The user
starts with a fuzzy investment intent and ends with a concrete paper trade plus
audit and replay proof.

Current status:

- thesis, catalog, basket, and portfolio schema code exists,
- static JSON fixtures exist for account, quotes, model response, allowed
  ticket, paper fill, and replay capsule,
- one Zig integration fixture validates parts of the allowed USD 2,000 path,
- no active `tktool`, `tkadpt`, or V1.1 `tkrepl` implementation exists,
- model and adapter outputs are mostly static fixtures, not tile-produced
  boundary results.

Missing:

- active V1.1 topology,
- `tkmodl` replay/fixture mode for the captured model response,
- minimal `tktool` request normalization,
- minimal `tkadpt` fixture adapter,
- ticket builder/checker that produces the allowed ticket from basket and
  quote fixtures,
- audit hash-chain generation for the allowed run,
- replay validation against generated records, not only static JSON.

## Scenario 2: Oversized Trade Block

Input:

```text
Invest USD 25,000 in AI infrastructure for brokerage.demo_ops.
Use US-listed ETFs and large-cap equities.
Avoid leveraged/inverse products and keep single-name weight <= 25%.
```

Expected output:

- same thesis family and basket logic as the allowed trade,
- affordability shows the account has enough raw cash/buying power,
- policy blocks the trade because the V1.1 per-order paper limit is USD 2,500,
- max affordable/effective allowed amount is shown,
- no paper fill is emitted,
- audit records the deny reason,
- replay reproduces the deny without live model or adapter calls.

Why this matters:

It demonstrates Tickoni is not just an idea generator. It can say "no" even
when the account appears to have enough money.

Current status:

- static oversized thesis and blocked ticket fixtures exist,
- no executable test currently proves the USD 25,000 block path end to end,
- no generated audit fixture exists for the oversized blocked path,
- no V1.1 replay validates the block.

Missing:

- policy limit check wired through `tkpoly` for the ticket,
- blocked ticket generated by code rather than trusted as static JSON,
- audit record for `per_order_notional_exceeded`,
- replay assertion for the same blocked reason and max amount,
- proof that no `tkadpt` paper fill call occurs.

## Scenario 3: Restricted Instrument Block

Input examples:

```text
Buy SOXL in the AI infrastructure basket.
```

or:

```text
Include BULZ in the AI infrastructure basket.
```

Expected output:

- restricted instrument is identified before it reaches paper placement,
- failed scope dimension is `restricted_instrument` or asset class,
- no trade ticket line for the restricted ticker,
- no quote or paper-fill adapter call for the restricted ticker,
- audit records the denial,
- replay reproduces the denial with no external effects.

Why this matters:

It is the clearest safety proof. Leveraged and inverse ETFs are easy for a
reviewer to understand, and the block happens before money-adjacent action.

Current status:

- catalog marks restricted instruments such as `SOXL`, `SOXS`, and `BULZ`,
- basket tests already prove restricted AI infrastructure instruments do not
  enter the normal allowed basket,
- static restricted-request and blocked-ticket fixtures exist,
- no executable V1.1 scenario proves direct restricted user input is denied
  before adapter work,
- the current restricted fixture uses a mixed FAANG/private-company example,
  which is less direct than `SOXL` or `BULZ`.

Missing:

- direct restricted-instrument scenario using `SOXL` or `BULZ`,
- policy denial through `tkpoly`,
- no-adapter-call assertion,
- audit records for the restricted denial,
- replay of the denial path.

## Scenario 4: Replay Tamper Detection

Input:

1. Run the allowed USD 2,000 demo.
2. Replay it against one deliberately changed model, quote, ticket, or paper
   fill hash.

Expected output:

- replay runs with external effects disabled,
- no live model call occurs,
- no live adapter or paper-fill call occurs,
- replay reports a divergence,
- first divergent field or sequence is visible,
- audit/replay output is inspectable.

Why this matters:

This is the strongest proof artifact. It shows Tickoni can detect drift or
tampering instead of merely logging a nice story.

Current status:

- Phase 0 payment replay exists and compares regenerated payment audit events,
- V1.1 replay capsule fixture exists,
- the V1.1 replay capsule uses symbolic hashes,
- there is no V1.1 replay engine that substitutes model and adapter outputs
  from the capsule and detects tamper.

Missing:

- V1.1 replay capsule parser or fixture loader,
- substitution lookup for model response, portfolio, quote, and paper fill,
- replay comparison for basket, ticket, policy, adapter, and audit records,
- deliberate tamper fixture,
- test that proves no external effects occur during replay.

## Mocked Tiles And Replacement Plan

For the lean demo, some tiles can begin as deterministic in-process
implementations. They should still expose the right ownership boundary.

### `tkcase`

Initial demo implementation:

- derive one synthetic run id from the thesis input hash and policy version,
- attach every later record to that run id.

Replace later with:

- real deterministic case lifecycle state,
- case ordering,
- evidence attachment.

### `tkdisp`

Initial demo implementation:

- dispatch exactly one bounded investment-demo work item.

Replace later with:

- queue-backed agent scheduling,
- priority,
- cancellation,
- budget-aware dispatch.

### `tkagnt`

Initial demo implementation:

- deterministic demo agent function,
- calls `tkmodl` for model recommendation,
- calls `tktool` for portfolio, quotes, and paper order,
- never calls model or adapter code directly.

Replace later with:

- sandboxed bounded agent worker,
- role-specific agent runtime,
- step limits and cancellation.

### `tktool`

Initial demo implementation:

- accept only:
  - `trading_portfolio.read`,
  - `market_event.read` or `quote_snapshot.read`,
  - paper `trading_order.place`,
- normalize each request into a finance-native adapter envelope,
- reject any unknown tool name.

Replace later with:

- broader model-native function-call normalization,
- MCP-compatible request handling,
- manifest-aware adapter routing.

### `tkadpt`

Initial demo implementation:

- fixture adapter only,
- returns:
  - `account_ops.json`,
  - `quotes.json`,
  - `paper_execution_allowed_2000.json`,
- denies paper fill unless ticket policy outcome is `allow`,
- records adapter request and response hashes.

Replace later with:

- signed adapter manifests,
- local broker sandbox,
- read-back reconciliation.

### `tkrepl`

Initial demo implementation:

- load one V1.1 replay capsule,
- substitute captured model and adapter outputs,
- recompute expected basket/ticket/policy/audit references,
- report first divergence.

Replace later with:

- generalized replay capsule runtime,
- multi-case replay,
- richer divergence reporting.

## How `tkmodl` And llama.cpp Fit

`tkmodl` is required for both deterministic and live model paths. llama.cpp is
only one optional provider behind `tkmodl`.

### Default deterministic lane

Used by:

- `just test-integration-tk`,
- the normal exec-facing demo,
- replay.

Behavior:

- `tkagnt` asks `tkmodl` for a model recommendation,
- `tkmodl` validates the model request scope, policy version, budget id, and
  model id,
- `tkmodl` returns the captured fixture response from
  `model_response_gemma4.json`,
- `tkmodl` emits audit-ready request/response references,
- no HTTP call occurs,
- no llama.cpp server is required.

This is the required proof lane.

### Live llama.cpp smoke lane

Used by:

- an explicit system/smoke recipe such as `just test-system-tk`
  (`just test-smoke-tkmodl-live` remains an alias),
- an optional demo mode when the local model server is intentionally running.

Behavior:

- `tkagnt` still calls `tkmodl`, not the HTTP backend,
- `tkmodl` validates the same request fields,
- `tkmodl` checks model allowlist and live-provider-enabled config,
- `tkmodl` builds a provider request,
- `HttpBackend` calls the local OpenAI-compatible llama.cpp endpoint,
- `tkmodl` records token usage, latency, request hash, response hash, model id,
  and replay substitution id,
- the captured response can be replayed later without llama.cpp.

This proves the harness can run a real local model, but it is not the normal CI
or deterministic proof lane.

### What llama.cpp must not do

- It must not be called directly by tests, agents, or demo commands.
- It must not be required for default integration.
- It must not own policy, budget, replay, or audit decisions.
- It must not be a hidden fallback when replay data is missing.

4. Replay capsule hash fields are symbolic strings — no hash verification runs on the normal path
The capsule JSONs use string placeholders ("proposal_hash_ticket_v1_1_ai_infra_2000_market") in fields declared as ?u64 in ReplayCapsuleWire. When parsed, these strings produce null, so expected_basket_id, expected_proposal_hash, and expected_response_hash are all null in the normal capsule — meaning every optional hash comparison in verifyAllowedTrade is skipped. The tamper test works only because the tampered capsule sets "expected_response_hash": 1 (a literal integer that doesn't match the computed hash).
