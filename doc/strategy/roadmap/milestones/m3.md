# M3: Product Packaging And Professional Terminal

## Description

M3 makes Tickoni deliverable to users and visible to operators:

```text
distributable package -> install/verify/update -> professional terminal
```

M3 ships the first runnable Tickoni package with installation, checksum verification, and update flows (V3.23), while V3.19 wraps those capabilities into a native professional terminal experience — a dense, keyboard-first Qt desktop application that turns investment intent into a policy-checked, explainable, and replayable proposal.

The terminal borrows workflow discipline and information density from professional financial terminals without copying proprietary branding. Distribution, installation, and verification make those capabilities accessible on any supported platform.

## Included Epics

- `V3.19`: Tickoni Native Investment Terminal
- `V3.23`: Distribute a Runnable Tickoni Package with Installation, Verification, and Update Flow

## Why This Is A Milestone

M2 establishes real and enforced tile runtime boundaries. M3 makes those capabilities visible, usable, and distributable to end users.

It deserves milestone status because it changes Tickoni from a runtime the team operates into a product the user installs, verifies, runs, and uninstalls — while retaining a professional terminal surface that makes policy-checked investment proposals the primary operator workflow.

The runtime boundaries from M2 (crash isolation, bounded agent runs, normalized tool dispatch, auditable model limits) become the trust surface behind the installer and the terminal. M3 closes the loop: build a professional terminal and ship it as a distributable package.

These properties are prerequisites for the proof and trust surfaces in M4.

## Completion Signal

M3 is complete when:

- A user on any supported platform can download a release artifact, verify its checksum, install without admin privileges, run `tickoni doctor`, and execute a deterministic paper demo.
- The native Tickoni terminal renders the AI-infrastructure case with normalized intent, account state, basket, policy outcome, before/after impact, proposal identity, and replay status — without requiring the operator to read fixture output, audit JSONL, replay logs, or diagnostic files.
- The restricted `SOXL` scenario shows the exact denied reason and exposes no quote or paper-action affordance for the rejected instrument.
- The terminal handles missing, stale, malformed, or unavailable state without rendering it as allowed.
- The installed runtime produces identical replay results to the source-build for the same fixture.
