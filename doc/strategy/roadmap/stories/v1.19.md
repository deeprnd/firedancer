# V1.19: Tickoni Terminal CaseOps UI

**Status:** Backlog
**Milestone:** M3
**Labels:** `epic`, `operations`, `trust`, `platform`, `audit`, `investing`,
`payments`, `enhancement`

Build the first dense financial terminal surface for Tickoni: a keyboard-first
CaseOps UI that turns money intent, policy decisions, proposals, impact,
audit, replay, adapter status, and runtime health into one operator-visible
control plane. The UI borrows the seriousness and density of financial
terminals, but its dominant object is the policy-checked consequence, not PnL,
ranking, or autonomous trading performance.

This epic fits the architecture as an attached CaseOps surface over `tkapi`.
The UI does not own financial correctness. It reads governed state from
Tickoni-owned API, audit, replay, metrics, and diagnostics surfaces, and it
submits review or proposal actions only through `tkapi` contracts that route
back into the owning tiles.

## Product Intent

Tickoni needs a visible product surface that makes the framework promise
obvious: financial intent becomes a policy-checked, replayable proposal before
money consequence. Current roadmap increments prove domain flows and runtime
boundaries, but the operator still needs one place to inspect the normalized
intent, allowed or denied scope, proposed action, before/after impact,
evidence, replay status, and system health.

V1.19 delivers that terminal surface without inventing new financial policy or
execution authority. It visualizes and drives the existing governed path:

```text
intent -> policy -> proposal -> approval or paper action -> audit -> replay
```

## Users And Jobs

- Consumer-money user: enter or inspect a financial intent and see why the safe
  action is allowed, denied, approval-required, or evidence-required.
- CaseOps operator: review cases, evidence, proposals, denials, approvals, and
  replay status from one dense terminal workspace.
- Compliance or risk reviewer: inspect the exact policy gates, financial scope,
  evidence references, hashes, and replay outcome behind a proposal.
- Runtime owner: see tile, queue, adapter, metric, diagnostic, and degradation
  signals without reading raw logs.
- Partner reviewer: inspect an exported proof bundle and understand the
  capability catalog that governed the result.

- A deterministic local UI flow renders the V1.1 investment safe-action
  scenario from fixtures or `tkapi` mocks with normalized intent, basket,

- A deterministic local UI flow renders the V1.2 payment guard scenario from

- Replay and audit panels show event hash, policy hash, proposal hash,

  when present.
- Health panels expose queue, tile, adapter, API, replay, and diagnostic state
  sourced through Tickoni-owned surfaces, not Solana validator GUI schemas.
- UI tests or screenshots prove the terminal layout remains readable at desktop
  and narrow operator widths with no overlapping labels or hidden critical
  decisions.

## Architecture Fit

The architecture document places Next.js CaseOps outside the deterministic
event runtime and behind the Zig `tkapi` HTTP/WebSocket tile. V1.19 follows
that boundary:

- `tkapi` serves CaseOps board reads, evidence reads, approvals, audit timeline
  reads, replay status, and health fanout.
- `tkpoly` remains the only authority for finance-native policy outcomes.
- `tkaudt` remains the source of append-only material event history.
- `tkrepl` remains the source of replay match, divergence, and proof-bundle
  status.
- `tkmodl`, `tktool`, and `tkadpt` remain hard boundaries for model, tool, and
  adapter access.
- Future `tkexec` remains disabled unless a later approved-execution epic
  explicitly enables a sandbox or live path.

The UI may cache display data for responsiveness, but any cached data is only
presentation state. Reconstructable case, policy, audit, evidence, and replay
truth stays with the Tickoni runtime and its durable artifacts.

## Firedancer Reuse

V1.19 should reuse Firedancer infrastructure through Tickoni-owned surfaces,
not by exposing validator product schemas:

| Firedancer source | Reuse mode for V1.19 |
| --- | --- |
| `src/waltz/http` / `fd_http_server` | Use or wrap for `tkapi`, `tkmetr`, and `tkdiag` HTTP/WebSocket surfaces where practical. |
| `src/disco/metrics` patterns | Reuse metric workspace/rendering patterns for `tkmetr`; expose Tickoni metric names, not validator metrics as financial facts. |
| `src/disco/diag` patterns | Reuse process, queue, crash, CPU, and supervisor diagnostics ideas for `tkdiag`; remove validator health checks. |
| `src/tango` | Source of future shared-memory queue and flow-control signals surfaced in UI health panels. |
| `src/disco/topo` and `src/disco/stem` | Reference for topology, lifecycle, bounded polling, and backpressure state shown by the UI. |
| `src/util/sandbox` | Source of sandbox and per-tile isolation status surfaced by the UI when available. |

Validator GUI, RPC, plugin, Solana replay, Solana accounts, validator gossip,
PoH, bank, shred, repair, bundle, and snapshot tiles are out of scope. They may
inform low-level implementation patterns, but their schemas must not become
CaseOps contracts.

## Release / Evidence Gate

- What can the user or operator do now that they could not before this epic?
  Inspect Tickoni money decisions through one terminal surface instead of
  reading separate fixture output, audit JSONL, replay output, and diagnostic
  logs.
- What changed from the previous roadmap increment? V1.18 made proof bundles
  self-verifying; V1.19 makes those proofs, policies, decisions, and runtime
  health operator-visible.
- What is this epic's wow-effect? A single terminal screen shows intent,
  consequence, policy decision, rejected candidates, before/after impact,
  audit hashes, replay match, and health state together.
- How does this progress Tickoni's value proposition? It makes speed, control,
  bounded spend, policy-gated action, and forensic replay visible in the
  product surface without weakening runtime boundaries.
- Which demo command or CaseOps flow closes the epic? A deterministic local
  CaseOps terminal flow that renders the investment and payment guard fixtures
  plus an intentional denial and replay proof.
- Which financial checks are enforced, if any? The UI enforces no policy by
  itself. It displays checks produced by the owning runtime: account,
  beneficiary, rail, currency, market, venue, asset class, instrument, notional,
  amount, exposure, frequency, approval, and evidence state where available.
- What happens when the requested action exceeds policy, scope, or evidence?
  The terminal shows `deny`, `require_approval`, `require_more_evidence`, or
  `escalate` with the reason and disabled direct action controls.
- Is execution paper-only, draft-only, sandbox, live, or disabled? UI execution
  authority is disabled. It may display draft, proposal, approval, paper, or
  sandbox state only when the runtime provides that state.
- Which artifacts prove behavior? UI screenshots, fixture JSON, `tkapi` example
  responses, audit/replay samples, blocked-flow fixture, and focused UI/API
  tests.
- Can replay run without external side effects when replay applies? Yes; replay
  status is read from `tkrepl` or deterministic replay fixtures, and the UI
  does not invoke external providers.
- What intentional blocked flow proves fail-closed behavior? Restricted
  instrument, out-of-scope beneficiary, missing evidence, stale replay capsule,
  and degraded adapter fixtures all render blocked or unavailable states.

## V1.19.S7: API Contracts, Fixtures, Screenshots, And Release Evidence

**Status:** Backlog
**Epic:** V1.19
**Parent roadmap item:** V1.19: Tickoni Terminal CaseOps UI
**Labels:** `story`, `documentation`, `enhancement`

Define the minimum `tkapi` read/review contracts and evidence pack needed to
verify the terminal UI without weakening runtime boundaries.

### Product Outcome

Implementers, reviewers, and partners can see exactly which API shapes,
fixtures, screenshots, and tests prove the terminal behavior and no-bypass
guarantees.

### User Story

As a developer/operator, I want the UI contracts and evidence pack documented,
so that implementation can proceed without inventing policy, storage, adapter,
or execution semantics inside the frontend.

### Scope

- In scope: minimum read response examples for terminal panels, fixture paths,
  screenshot checklist, blocked-flow examples, focused test commands, and
  contract notes for `tkapi`, `tkmetr`, and `tkdiag`.
- Out of scope: implementing new runtime endpoints, changing public contracts
  beyond documented read/review needs, or adding live external dependencies.

### Preconditions And Assumptions

- If an endpoint does not exist, this story documents the required contract
  before implementation work begins.
- Contract examples must preserve architecture boundaries and source-of-truth
  roles.

### Acceptance Criteria

- [ ] Given this epic, when implementation starts, then every UI panel has a
      fixture or documented `tkapi` read response with source, freshness, and
      unavailable-state fields.
- [ ] Given a sensitive action affordance, when no approved runtime contract
      exists, then the UI contract marks the action disabled or proposal-only.
- [ ] Given release review, when evidence is collected, then screenshots,
      blocked-flow fixtures, and focused test commands are linked from this
      roadmap item.

### Conditional Acceptance

**Financial capability and policy**

- [ ] Contract examples carry policy version, outcome, reason, and relevant
      scope fields where policy applies.

**Audit and replay**

- [ ] Contract examples carry hashes, evidence refs, replay capsule id, status,
      and divergence fields where audit/replay applies.

**Runtime topology and tile ownership**

- [ ] Contract examples for health identify Tickoni tile IDs, links, producer,
      consumer, depth, reliability, and degraded state where available.

**Model, tool, adapter, or execution boundary**

- [ ] Contract examples include attribution and status only; no direct model,
      tool, adapter, or execution credentials appear in UI fixtures.

**CaseOps API or UI**

- [ ] `tkapi` is documented as the only UI boundary for case, evidence,
      proposal, approval, audit, replay, and health fanout.

### Evidence Plan

- Demo or command: documentation review plus local fixture-driven terminal run.
- Tests: schema/example validation and focused UI fixture tests.
- Fixtures or samples: investment, payment, impact, replay, capability,
  adapter, metric, and diagnostic examples.
- Audit/replay evidence: clean replay, tamper, stale capsule, and missing
  evidence examples.
- Blocked-flow evidence: restricted instrument, out-of-scope beneficiary,
  degraded adapter, unknown command, and unavailable impact examples.
