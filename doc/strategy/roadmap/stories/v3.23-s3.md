# V3.23.S3: Update and uninstall — safe update path preserving evidence, uninstall preserving evidence by default, full reset opt-in

**Status:** Backlog
**Epic:** #[github-epic-issue] (V3.23)
**Parent roadmap item:** V3.23: Distribute a Runnable Tickoni Package with Installation, Verification, and Update Flow
**Labels:** `type/story`, `area/operations`, `type/feature`

<!-- One sentence: the independently verifiable deliverable. -->

A user can safely update Tickoni to a new version without losing audit evidence,
replay artifacts, or demo manifests. The update replaces binaries and runtime
files but preserves `~/.tickoni/evidence/` and `~/.tickoni/demos/`. An uninstall
path removes binaries but preserves evidence by default. A full reset (removing
everything including evidence) requires explicit opt-in.

## Product Outcome

A user who has installed Tickoni can update to a new version by downloading the
new tarball, verifying checksums, and running the installer again. Their audit
evidence and demo manifests survive the update. If they want to remove Tickoni,
the uninstall removes binaries but preserves evidence unless they explicitly
request a full reset.

## User Story

As a consumer-money user, I can upgrade to a new Tickoni version without
re-downloading my audit evidence or demo manifests. The update installs fresh
binaries while keeping my existing evidence intact.

As a partner reviewer or auditor, I can uninstall Tickoni to clean up my machine
while preserving the audit evidence I need for review, or do a full reset if I
want everything gone.

## Scope

- In scope:
  - Update path: documentation and installer support for replacing binaries while
    preserving `~/.tickoni/evidence/` and `~/.tickoni/demos/`.
  - Update verification: checksum verification before update, version check
    after update, doctor output comparison after update.
  - Uninstall path: documentation and uninstaller scripts that remove binaries
    (`tickoni`, `tickoni-supervisor`) and the runtime directory structure
    (`~/.tickoni/bin/`, `~/.tickoni/demos/`, `~/.tickoni/logs/`, `~/.tickoni/tmp/`)
    but preserve evidence (`~/.tickoni/evidence/`) by default.
  - Full reset opt-in: an `--evidence` or `--all` flag on the uninstaller to
    also remove evidence and demo files.
  - All paths are user-scoped — no admin/sudo required.
  - Source-build workspace cleanup documented (`rm -rf zig-out build .zig-cache`).

- Out of scope:
  - Automatic background self-update.
  - Rollback to previous version.
  - Migrating evidence between different user-scoped install locations.
  - Cross-platform unified uninstaller binary.

## Preconditions And Assumptions

- V3.23.S1 produces versioned release tarballs.
- V3.23.S2 produces installers that create the standard `~/.tickoni/` directory
  structure.
- `retail-runtime-support.md` documents the expected directory layout and the
  update/uninstall paths (the docs already describe this; the implementation
  needs to match).
- Evidence files (`~/.tickoni/evidence/`) are append-only audit JSONL, replay
  capsules, and conformance comparison results — they must not be modified by
  the update or uninstall.

## Acceptance Criteria

- [ ] Given an installed Tickoni runtime with evidence files, when a user runs
      the installer with a new version's tarball, then binaries are replaced in
      `~/.tickoni/bin/` and `~/.tickoni/evidence/` and `~/.tickoni/demos/`
      are preserved intact.
- [ ] Given an installed Tickoni runtime, when a user runs the uninstaller
      without the `--evidence` flag, then binaries and runtime directories are
      removed but `~/.tickoni/evidence/` is preserved.
- [ ] Given an installed Tickoni runtime, when a user runs the uninstaller with
      the `--evidence` (or `--all`) flag, then everything under `~/.tickoni/`
      is removed.
- [ ] Given a Linux/macOS environment, when the uninstaller runs, then
      `rm` operations target only the `~/.tickoni/` directory and do not
      affect other user files.
- [ ] Given a Windows environment, when the uninstaller runs, then removal
      targets only `%LOCALAPPDATA%\tickoni\` and does not affect other user data.
- [ ] Given a successful uninstall, when the user re-runs `tickoni --version`,
      then the command is not found or returns a diagnostic indicating Tickoni
      is not installed.
- [ ] Given a successful uninstall, when the user inspects `~/.tickoni/`, then
      evidence files are still present (without the `--evidence` flag).

## Child Task Issues

Create sub-issues only after this story is `Ready`.

V3.23.S3.T1 — Architecture and planning. Define the update strategy (replace-only
vs. backup-then-replace), uninstall target paths, evidence preservation logic,
and full-reset opt-in interface. Decide on flag names and help text.

V3.23.S3.T2 — Update path implementation. Enhance `install.sh` and `install.ps1`
to detect an existing installation and offer an upgrade path. The upgrade replaces
binaries in `~/.tickoni/bin/` without removing evidence.

V3.23.S3.T3 — Uninstaller scripts. Create `uninstall.sh` (Linux/macOS) and
`uninstall.ps1` (Windows) that: (a) without flags — remove binaries and runtime
dirs but preserve evidence; (b) with `--evidence` flag — remove everything under
`~/.tickoni/`.

V3.23.S3.T4 — Verification logic. Implement post-install post-uninstall checks:
`tickoni --version` after update, `tickoni doctor` after update, file count check
for evidence preservation, PATH reset check after uninstall.

V3.23.S3.T5 — Documentation and DevOps sweep. Update `retail-runtime-support.md`
with the update path and uninstall path (align with what the implementation does),
update `doc/execution/development.md`, update the justfile with release/update
targets.

V3.23.S3.T6 — Security audit. Verify uninstallers do not remove files outside
`~/.tickoni/`, do not modify system files, and that evidence preservation is
the default behavior (not destructive by accident).

V3.23.S3.T7 — Telemetry audit. Verify no outbound calls during update or uninstall.

V3.23.S3.T8 — Evidence and quality gate. Test the full lifecycle: install →
generate evidence → update to new version → verify evidence intact → uninstall
(without evidence flag) → verify evidence preserved → uninstall with evidence
flag → verify everything removed. Update roadmap.

## Notes And Open Questions

- Should the uninstaller be a standalone script, or integrated into the installer
  with a `--uninstall` flag?
- Should evidence be zipped or compressed before uninstall to preserve it as a
  portable artifact?
- How do we handle the case where the user's evidence directory has grown large
  (e.g., many replay capsules)?
- Should the update check for version compatibility (e.g., reject downgrades, warn
  about evidence format changes)?
