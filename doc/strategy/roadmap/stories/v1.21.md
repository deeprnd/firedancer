# V1.21: Cross-Platform Retail Runtime Support

**Status:** Backlog
**Milestone:** M2
**Labels:** `epic`, `platform`, `operations`, `security`, `trust`, `enhancement`

Build on V1.14's Firedancer process and shared-memory topology work so Tickoni
can be built, installed, and run by broad consumer and developer users on
macOS, Windows, Linux, and ordinary consumer hardware without weakening the
high-throughput Firedancer engine or Tickoni's financial control boundaries.

The intended end state is not to disguise every host as an equivalent
production engine. Tickoni must expose explicit runtime support tiers:
Linux remains the full high-throughput Firedancer tile runtime unless a later
architecture decision proves native parity, while macOS and Windows gain a
supported retail runtime path for deterministic paper/sandbox demos, policy
decisions, audit output, and replay proofs.

## Product Intent

Consumer users, reviewers, and developer-community evaluators should not need a
tuned Linux workstation before they can inspect a policy-gated money proposal,
audit trail, or replay proof. V1.21 turns platform support into part of the
trust surface: every build, installer, demo, and audit artifact must say which
Tickoni version, host OS, architecture, runtime tier, and isolation guarantees
produced it.

This continues V1.14 by deciding how the Linux process/shared-memory topology
is exposed to retail users without forcing unsafe portability shortcuts into
Firedancer substrate. Minimal adaptation of Firedancer tiles and code is a
constraint: reuse or wrap generic substrate deliberately, exclude Solana
validator semantics from distributed artifacts, and keep platform-specific
substitutes behind Tickoni-owned support-tier decisions.

## Users And Jobs

- Consumer-money user: run a local Tickoni demo on a MacBook, Windows laptop,
  or Linux desktop and see policy decisions, proposal hashes, audit output, and
  replay proof before any live money path exists.
- Developer-community evaluator: build and run the supported retail runtime on
  common hardware with clear preflight failures instead of reverse-engineering
  Linux-only Firedancer assumptions.
- CaseOps operator or partner reviewer: know exactly which platform tier and
  Tickoni version produced a proposal or replay artifact.
- Runtime owner: preserve the high-throughput Linux Firedancer engine while
  making portable runtime limits, sandbox gaps, and unsupported features
  visible and fail-closed.
- Security reviewer: verify installers, checksums or signatures, no-secrets
  defaults, per-user install locations, disabled live execution, and no hidden
  privilege escalation.

## Success Metrics

- A supported macOS and Windows retail path can build or install Tickoni and
  run the selected deterministic paper/sandbox demo on consumer hardware.
- `tickoni --version`, `tickoni doctor`, and demo preflight output identify
  Tickoni version, build id, git revision or release digest, OS, architecture,
  runtime tier, isolation tier, demo compatibility, and live-execution status.
- Deterministic fixture flows produce equivalent normalized event hashes,
  policy outcomes, proposal hashes, audit records, and replay results across
  Linux full-runtime mode and supported retail modes.
- Unsupported host capabilities, missing WSL2/container/VM/native prerequisites,
  stale demo manifests, unsupported CPU/OS combinations, and attempted live
  execution fail closed with actionable diagnostics.
- Consumer packages include only Tickoni-owned code and the Firedancer substrate
  Tickoni actually reuses; Solana validator tiles, RPC schemas, and unrelated
  source are excluded.
- Install and update paths provide a manual verification route with checksums,
  signatures, or attestations, and do not request broker, payment, crypto,
  TigerBeetle, or live model-provider credentials.

## Demo Moment

- Command or flow: install or build Tickoni on a supported macOS and Windows
  machine, run `tickoni doctor`, then run the selected retail demo manifest for
  a deterministic paper investment or money-movement proposal.
- Expected result: the user sees the platform tier, disabled live execution,
  policy-checked proposal, audit JSONL, replay match, version/provenance
  metadata, and a blocked-flow example when the host or demo version is
  unsupported.

## Scope

### In Scope

- Define official support tiers for Linux full-runtime, macOS retail runtime,
  Windows retail runtime, container/WSL2/VM-assisted modes, and unsupported hosts.
- Decide the first macOS and Windows support paths: native portable mode,
  Linux container, WSL2, VM packaging, or a documented hybrid.
- Inventory Linux-only Firedancer and Tickoni assumptions that affect consumer
  build/run support, isolation, determinism, packaging, or conformance.
- Limit build, test, and coverage to only the Firedancer modules Tickoni
  actually reuses for retail modes — Mac/Win must not try to port what it does
  not need.
- Decide target-specific Tickoni C ABI bridge behavior: Linux may link real
  Firedancer libraries, while macOS and Windows retail modes must either link
  only proven-portable Firedancer subsets or use Tickoni-owned substitutes.
- Preserve the high-throughput Firedancer engine as the Linux full-runtime tier
  while allowing consumer hardware to run supported proof/demo flows.
- Add version, build metadata, release digest, platform tier, isolation tier,
  and demo-manifest compatibility requirements to the product plan.
- Plan official install, update, uninstall, checksum/signature, and manual
  verification paths for Linux/macOS and Windows.
- Make platform mode and degraded guarantees visible in CLI, CaseOps, audit,
  replay, metrics, diagnostics, and documentation where they affect trust.
- Define cross-platform conformance evidence for deterministic fixture flows.
- Define package inclusion rules so only reused Firedancer substrate ships in
  consumer artifacts.

### Out Of Scope

- No silent port of the full Firedancer hot path to macOS or Windows.
- No throughput-parity claim for macOS or Windows before measured evidence.
- No weakening of capability envelopes, audit hash chaining, replay
  substitution, adapter boundaries, sandbox expectations, or fail-closed
  behavior for portability.
- No live trading, payments, crypto transfers, ledger posting, TigerBeetle
  writes, or privileged execution on consumer Mac/Windows modes.
- No production financial credentials during install, preflight, first run, or
  demo.
- No replacement of the Tickoni tile architecture with a generic cross-platform
  service backend.
- No direct import of Solana validator tile identities, RPC schemas, or
  validator runtime assumptions into Tickoni platform support.
- No assumption that `libfd_tango.a`, `libfd_util.a`, or `libfd_ballet.a`
  compile, link, or export the same symbols natively on macOS or Windows.
  Runtime `if supported` checks are not sufficient when the compiler or linker
  cannot resolve the Firedancer symbol in the first place.

# V1.21.S1: Platform support tier definitions

**Status:** Backlog
**Epic:** #[github-epic-issue]
**Parent roadmap item:** V1.21: Cross-Platform Retail Runtime Support
**Labels:** `story`, `platform`, `enhancement`

Define official runtime support tiers and their scope before any macOS or
Windows implementation hardens Linux-only assumptions.

## Product Outcome

Users and developers know whether their host is supported, which runtime tier
they are using, and which guarantees are unavailable before they run a
money-adjacent demo.

## User Story

As a developer-community evaluator, I want Tickoni to name the supported
runtime tier for my Mac or Windows machine, so that I can run the right demo
path without assuming Linux-equivalent performance or isolation.

## Scope

- In scope: define tier language, map workflows to tiers, specify degraded-
  guarantee visibility rules.
- Out of scope: macOS/Windows implementation decisions (separate stories),
  Firedancer porting (S2), installer design (S4/S5).

## Preconditions And Assumptions

- V1.14 established the Linux full-runtime tier with Firedancer process and
  shared-memory topology.
- Linux remains the default high-throughput tier unless a separate decision
  approves native parity.

## Acceptance Criteria

- [ ] Given a host OS and architecture, when the user checks tier definitions,
      then the output identifies Linux full-runtime, macOS retail runtime,
      Windows retail runtime, container/WSL2/VM-assisted mode, or unsupported.
- [ ] Given a supported tier, when the user selects a workflow, then the tier
      explicitly states which workflows are supported (build-only,
      doctor-only, deterministic paper demo, CaseOps review, replay proof,
      sandbox adapter substitute, full Linux tile runtime) and which are not.
- [ ] Given degraded guarantees (performance, sandboxing, networking, shared
      memory, execution), when the runtime reports tier status, then the
      degradation is visible in CLI, CaseOps, audit, replay, and docs.

# V1.21.S2: Build scope filter for retail targets

**Status:** Backlog
**Epic:** #[github-epic-issue]
**Parent roadmap item:** V1.21: Cross-Platform Retail Runtime Support
**Labels:** `story`, `platform`, `enhancement`

Limit build, test, and coverage for macOS and Windows retail targets to only
the Firedancer modules Tickoni actually reuses. Define a compile-time or
build-time gating mechanism so Mac/Win builds do not attempt to port what
they do not need.

## Product Outcome

Consumer packages include only Tickoni-owned code and the Firedancer substrate
Tickoni actually reuses, and Mac/Win builds fail fast at compile time instead
of silently trying to port unneeded modules.

## User Story

As a runtime owner, I want the build system to exclude non-reused Firedancer
modules from Mac/Win retail targets, so that I do not waste time porting code
that Tickoni will never call.

## Scope

- In scope: define build-scope rules, define package-inclusion rules, define
  target-selected linking rules for Firedancer archives, inventory Linux-only
  assumptions and classify them, provide a build-time gate so retail targets
  only compile what they reuse.
- Out of scope: macOS/Windows implementation (S4/S5), installer packaging
  (S4/S5), demo/conformance (S6), docs (S7).

## Preconditions And Assumptions

- V1.14 defined the Linux full-runtime build path; Mac/Win targets need a
  narrower surface.
- Firedancer is a dependency; Tickoni may reuse infrastructure primitives
  (queues, topology, workspaces, sandboxing, metrics, diagnostics, HTTP) but
  must not import Solana validator semantics.

## Acceptance Criteria

- [ ] Given a macOS or Windows retail build target, when the build runs, then
      only Firedancer modules Tickoni actually reuses are compiled and linked.
- [ ] Given a retail target that references a Linux-only Firedancer symbol
      (e.g. hugetlbfs, XDP, eBPF, io_uring, CPU affinity, /proc access),
      when the build is evaluated, then compilation fails with a clear error
      identifying the missing symbol and its classification.
- [ ] Given the Firedancer reuse inventory, when a reviewer examines it, then
      each Linux-only assumption is classified as full-runtime only, retail-
      runtime substitute, packaging precondition, unsupported, or decision-
      needed.
- [ ] Given package reporting, when coverage is measured, then it reports only
      Firedancer code actually reused by Tickoni, excluding Solana validator
      tiles, RPC schemas, and unrelated source.

### Conditional Acceptance

**Financial capability and policy**

- [ ] N/A - story affects build rules, not policy.

**Audit and replay**

- [ ] N/A - build scope does not change audit/replay semantics.

**Runtime topology and tile ownership**

- [ ] N/A - story defines build-time inclusion rules, not tile ownership or
      link shape.

**Model, tool, adapter, or execution boundary**

- [ ] N/A - build scope does not modify model/tool/adapter boundaries.

**CaseOps API or UI**

- [ ] N/A - story affects build, not API or UI.

## Child Task Issues

- V1.21.S2.T1 — Inventory Linux-only Firedancer assumptions (build profiles,
  x86-64 TSO, SSE/AVX, hugetlbfs, shared memory, NUMA, memlock, /proc, CPU
  affinity, signals, sandboxing, XDP/AF_XDP, netlink, eBPF, io_uring, repo
  command recipes).
- V1.21.S2.T2 — Classify each assumption as full-runtime only, retail-runtime
  substitute, packaging precondition, unsupported, or decision-needed.
- V1.21.S2.T3 — Define the reusable package surface: `src/tango`, selected
  topology/workspace/process patterns, sandbox wrappers where supported,
  metrics/diagnostics patterns, `fd_http_server`, and Tickoni-owned Zig runtime
  modules.
- V1.21.S2.T4 — Define target-selected linking rules for `libfd_tango.a`,
  `libfd_util.a`, `libfd_ballet.a`; retail builds must not compile shims
  referencing missing Linux-only symbols.
- V1.21.S2.T5 — Define package inclusion rules and coverage reporting: exclude
  Solana validator tiles, RPC schemas, unrelated Firedancer source.
- V1.21.S2.T6 — Define the build-time gate mechanism so retail targets fail
  compile when they reference non-included Firedancer symbols.

## Evidence Plan

- Demo or command: build Tickoni on macOS or Windows with a retail target and
  verify that Linux-only symbols fail cleanly.
- Tests: `zig build test` (or equivalent) on Mac/Win retail target.
- Fixtures or samples: Build-scope manifest or table.
- Audit/replay evidence: N/A - story does not change audit/replay.
- Blocked-flow evidence: Compile attempt referencing a non-included Firedancer
  symbol should produce a clear error.

## Quality Gate

- [ ] Build-scope rules are codified before any Mac/Win implementation stories
      start.
- [ ] No story can assume that `libfd_tango.a`, `libfd_util.a`, or
      `libfd_ballet.a` compile natively on Mac/Win without a build-time gate.
- [ ] Documentation and roadmap status are updated when build rules change.

## Notes And Open Questions

- What is the exact build mechanism (build.zig conditions, justfile targets,
  compile-time flags) for the retail filter?
- How do Mac/Win stories (S4/S5) declare which modules they actually need?
