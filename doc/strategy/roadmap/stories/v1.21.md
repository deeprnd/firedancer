# V1.21: Cross-Platform Retail Runtime Support

**Status:** Backlog
**Milestone:** M2
**Labels:** `epic`, `platform`, `operations`, `security`, `trust`, `enhancement`

Build on V1.14's Firedancer process and shared-memory topology work so Tickoni
can be built, installed, and run by broad consumer and developer users on
macOS, Windows, Linux, and ordinary consumer hardware without weakening the
high-throughput Firedancer engine or Tickoni's financial control boundaries.

The intended end state is not to disguise every host as an equivalent
production engine. Tickoni must expose explicit runtime support tiers:
Linux remains the full high-throughput Firedancer tile runtime unless a later
architecture decision proves native parity, while macOS and Windows gain a
supported retail runtime path for deterministic paper/sandbox demos, policy
decisions, audit output, and replay proofs.

## Product Intent

Consumer users, reviewers, and developer-community evaluators should not need a
tuned Linux workstation before they can inspect a policy-gated money proposal,
audit trail, or replay proof. V1.21 turns platform support into part of the
trust surface: every build, installer, demo, and audit artifact must say which
Tickoni version, host OS, architecture, runtime tier, and isolation guarantees
produced it.

This continues V1.14 by deciding how the Linux process/shared-memory topology
is exposed to retail users without forcing unsafe portability shortcuts into
Firedancer substrate. Minimal adaptation of Firedancer tiles and code is a
constraint: reuse or wrap generic substrate deliberately, exclude Solana
validator semantics from distributed artifacts, and keep platform-specific
substitutes behind Tickoni-owned support-tier decisions.

## Users And Jobs

- Consumer-money user: run a local Tickoni demo on a MacBook, Windows laptop,
  or Linux desktop and see policy decisions, proposal hashes, audit output, and
  replay proof before any live money path exists.
- Developer-community evaluator: build and run the supported retail runtime on
  common hardware with clear preflight failures instead of reverse-engineering
  Linux-only Firedancer assumptions.
- CaseOps operator or partner reviewer: know exactly which platform tier and
  Tickoni version produced a proposal or replay artifact.
- Runtime owner: preserve the high-throughput Linux Firedancer engine while
  making portable runtime limits, sandbox gaps, and unsupported features
  visible and fail-closed.
- Security reviewer: verify installers, checksums or signatures, no-secrets
  defaults, per-user install locations, disabled live execution, and no hidden
  privilege escalation.

## Success Metrics

- A supported macOS and Windows retail path can build or install Tickoni and
  run the selected deterministic paper/sandbox demo on consumer hardware.
- `tickoni --version`, `tickoni doctor`, and demo preflight output identify
  Tickoni version, build id, git revision or release digest, OS, architecture,
  runtime tier, isolation tier, demo compatibility, and live-execution status.
- Deterministic fixture flows produce equivalent normalized event hashes,
  policy outcomes, proposal hashes, audit records, and replay results across
  Linux full-runtime mode and supported retail modes.
- Unsupported host capabilities, missing WSL2/container/VM/native prerequisites,
  stale demo manifests, unsupported CPU/OS combinations, and attempted live
  execution fail closed with actionable diagnostics.
- Consumer packages include only Tickoni-owned code and the Firedancer substrate
  Tickoni actually reuses; Solana validator tiles, RPC schemas, and unrelated
  source are excluded.
- Install and update paths provide a manual verification route with checksums,
  signatures, or attestations, and do not request broker, payment, crypto,
  TigerBeetle, or live model-provider credentials.

## Demo Moment

- Command or flow: install or build Tickoni on a supported macOS and Windows
  machine, run `tickoni doctor`, then run the selected retail demo manifest for
  a deterministic paper investment or money-movement proposal.
- Expected result: the user sees the platform tier, disabled live execution,
  policy-checked proposal, audit JSONL, replay match, version/provenance
  metadata, and a blocked-flow example when the host or demo version is
  unsupported.

## Scope

### In Scope

- Define official support tiers for Linux full-runtime, macOS retail runtime,
  Windows retail runtime, and unsupported hosts.
- Decide the first macOS and Windows support paths: native portable mode,
  Linux container, WSL2, VM packaging, or a documented hybrid.
- Inventory Linux-only Firedancer and Tickoni assumptions that affect consumer
  build/run support, isolation, determinism, packaging, or conformance.
- Decide target-specific Tickoni C ABI bridge behavior: Linux may link real
  Firedancer libraries, while macOS and Windows retail modes must either link
  only proven-portable Firedancer subsets or use Tickoni-owned substitutes.
- Preserve the high-throughput Firedancer engine as the Linux full-runtime tier
  while allowing consumer hardware to run supported proof/demo flows.
- Add version, build metadata, release digest, platform tier, isolation tier,
  and demo-manifest compatibility requirements to the product plan.
- Plan official install, update, uninstall, checksum/signature, and manual
  verification paths for Linux/macOS and Windows.
- Make platform mode and degraded guarantees visible in CLI, CaseOps, audit,
  replay, metrics, diagnostics, and documentation where they affect trust.
- Define cross-platform conformance evidence for deterministic fixture flows.
- Define package inclusion rules so only reused Firedancer substrate ships in
  consumer artifacts.

### Out Of Scope

- No silent port of the full Firedancer hot path to macOS or Windows.
- No throughput-parity claim for macOS or Windows before measured evidence.
- No weakening of capability envelopes, audit hash chaining, replay
  substitution, adapter boundaries, sandbox expectations, or fail-closed
  behavior for portability.
- No live trading, payments, crypto transfers, ledger posting, TigerBeetle
  writes, or privileged execution on consumer Mac/Windows modes.
- No production financial credentials during install, preflight, first run, or
  demo.
- No replacement of the Tickoni tile architecture with a generic cross-platform
  service backend.
- No direct import of Solana validator tile identities, RPC schemas, or
  validator runtime assumptions into Tickoni platform support.
- No assumption that `libfd_tango.a`, `libfd_util.a`, or `libfd_ballet.a`
  compile, link, or export the same symbols natively on macOS or Windows.
  Runtime `if supported` checks are not sufficient when the compiler or linker
  cannot resolve the Firedancer symbol in the first place.

- V1.21.S5.T6 - **Copy of V1.14.S8.T5** Real
  sandbox entry (`tk_sandbox_enter`) requires `unshare(CLONE_NEWUSER)` to
  drop to the `nobody` uid/gid `SandboxConfig` defaults to. Attempting
  this during implementation failed closed with `EPERM` in a session
  sandboxed by AppArmor's `apparmor_restrict_unprivileged_userns=1`
  (Ubuntu default since 23.10), even though the kernel itself allows
  unprivileged user namespaces (`unprivileged_userns_clone=1`) — i.e.
  the *kernel* supports it, but an unprivileged, un-profiled process
  cannot always create one, depending on the host's LSM configuration.
  Wiring real sandbox entry into the process-mode harness path as a
  required step would make Linux full-runtime process mode depend on a
  privilege regular consumer-tier users and hardened hosts may not
  have — directly contradicting V1.14.S1's "Tickoni must not inherit a
  hard... requirement" framing and V1.21's consumer-hardware goal. This
  is a product-architecture finding, not a workaround: **process
  isolation is not the same guarantee as namespace confinement.**
  Tickoni's crash-only model and per-tile OS-process isolation
  (supervisor-managed child processes, contained crashes, audited
  boundaries) already hold with `sandbox=0` throughout — namespace-level
  sandboxing is an optional hardening layer for hosts that support it,
  not a V1.14 correctness requirement. `SandboxConfig`
  (`src/tickoni/runtime/sandbox.zig`) stays defined, tested, and ready
  to be wired in; the harness call (`c_abi/shim/tile_run.c`'s
  `tk_topo_run_tile_simple`) keeps `sandbox=0`. Real wiring —
  including `tk_sandbox_enter` failing closed with a diagnostic
  (never escalating privileges or prompting for sudo) rather than
  crashing when namespaces are unavailable, and an explicit
  run-without-sandboxing fallback — is scoped to a V1.21 support-tier
  story once that story defines the actual capability/isolation model
  for hosts that can't create user namespaces. `generate_filters.py`'s
  topology-independence (traced to source, confirmed safe to use
  whenever this is picked back up) is preserved below for that future
  story.

  **Pre-validated: `generate_filters.py` is topology-independent.**
  The audit traced this to its source and confirmed the following:

  - `generate_filters.py` imports only Python stdlib (`os`, `sys`,
    `collections.OrderedDict`); it has zero Firedancer/Firedancer topology
    imports.
  - Input is a flat `.seccomppolicy` text file with a line-1 signature
    (e.g. `uint logfile_fd`) and lines of `syscall: [expr]` constraints;
    no topology objects, config structs, or Firedancer types are needed.
  - The only parameter a policy can reference is `uint` values (not
    pointers, not structs). Example: `fd_gossip_tile.seccomppolicy` has
    `uint logfile_fd` used as a symbolic constant in expressions.
  - Output is a standalone C header that includes only
    `fd_util_base.h`, linux/audit.h, linux/filter.h, linux/seccomp.h,
    linux/bpf.h, linux/unistd.h, sys/syscall.h, signal.h, stddef.h.
  - Generated headers declare a single function:
    `populate_sock_filter_policy_<tile>(ulong out_cnt, struct sock_filter
    out[static N])` — for parameterised policies the constructor adds
    uint parameters but no topology args.
  - `tk_sandbox_enter` (declared in `src/tickoni/c_abi/sandbox.zig`)
    takes the filter directly (`seccomp_filter_cnt`, `seccomp_filter`);
    the C substrate (`fd_sandbox.c`) accepts `struct sock_filter[]` — the
    exact output format. No topology context passes through the sandbox API.
  - The build integration (`everything.mk`) runs
    `$(FIND) . -name '*.seccomppolicy' | xargs $(PYTHON) generate_filters.py`
    — no Firedancer build system involvement beyond the PYTHON path.

  Tickoni writes one `.seccomppolicy` file per tile; the build pipeline
  produces `generated/<tile>_seccomp.h`; `tk_sandbox_enter` loads the
  filter at runtime. No build-time topology context is needed.
