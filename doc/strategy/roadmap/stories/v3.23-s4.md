# V3.23.S4: Distribution, verification, docs, and evidence gate — winget packages, checksum publishing, CI release workflow, evidence artifacts, roadmap reconciliation

**Status:** Backlog
**Epic:** #[github-epic-issue] (V3.23)
**Parent roadmap item:** V3.23: Distribute a Runnable Tickoni Package with Installation, Verification, and Update Flow
**Labels:** `type/story`, `type/documentation`, `type/feature`

<!-- One sentence: the independently verifiable deliverable. -->

The final story for V3.23 — this is the closure story that ties together the
release pipeline, installers, update/uninstall flows, and documentation. It
produces the winget package for Windows, publishes checksums to the GitHub
release, updates `retail-runtime-support.md` and `platform-tiers.md` to reflect
the new distribution surface, runs the full demo on a released artifact (not
source build), and completes all evidence gates and roadmap reconciliation.

## Product Outcome

A verified release of Tickoni is available for download on all supported platforms
and architectures. A user can follow the documented install path, verify checksums,
run doctor and demo, update, and uninstall — all without admin rights. The docs
accurately describe the shipped capability, the platform tiers are updated, and
the V2.22/V2.21 epics are reconciled.

## User Story

As a consumer-money user or developer-community evaluator, I can find a
verifiable Tickoni release, follow the documented install steps, run a demo, and
trust that the install, update, and uninstall paths described in the docs actually
work.

As a runtime owner and auditor, I can verify that the documented paths match
what was actually shipped — the docs are not speculative.

## Scope

- In scope:
  - Winget package publication for Windows releases.
  - Checksum publishing: ensure `checksums.txt` is published alongside each
    release and is machine-readable for automated verification.
  - Update `retail-runtime-support.md`: finalize the install path, update path,
    uninstall path, and manual verification path to reflect the actual
    implementation from S1-S3 (not the pre-implementation documentation from
    V2.21).
  - Update `platform-tiers.md`: add `windows_retail` as officially supported in
    V3.23 (runtime was supported in V2.22, distribution added in V3.23).
  - Update `V2.21.md` and `V2.22.md`: update their "Done" status to reference
    V3.23 for the missing installer/distribution pieces.
  - Demo on a released artifact: install from V3.23.S1 artifact using V3.23.S2
    installer, run `tickoni doctor` and the demo, capture evidence.
  - Complete all evidence artifacts for V3.23: version output, doctor output,
    demo output, checksum verification log, uninstall evidence.
  - Run the full closing gate per `doc/execution/quality.md`.

- Out of scope:
  - Signed release artifacts (Sigstore, GPG, minisign).
  - App-store distribution (Microsoft Store, Homebrew tap, Linux distro repos).
  - Windows MSI installer or macOS `.pkg`.
  - Automatic background self-update.

## Preconditions And Assumptions

- V3.23.S1 release pipeline produces working tarballs with checksums.
- V3.23.S2 installers work on all supported platforms.
- V3.23.S3 update and uninstall paths work correctly.
- V2.21.S4 and V2.22.S4 have produced working runtime binaries on macOS and
  Windows respectively.
- `retail-runtime-support.md` exists with V2.21-era documentation that needs
  updating to reflect V3.23 implementations.

## Acceptance Criteria

- [ ] Given a V3.23 release, when a user downloads the tarball and verifies
      SHA256 against the published `checksums.txt`, then the checksum matches.
- [ ] Given a V3.23 release, when a user runs the installer on any supported
      platform, then the installed runtime produces correct `tickoni --version`
      and `tickoni doctor` output.
- [ ] Given an installed V3.23 runtime, when a user runs the demo manifest,
      then the demo produces deterministic paper/sandbox output with audit
      JSONL and replay evidence.
- [ ] Given a V3.23 release, when the winget manifest is parsed, then it contains
      valid Windows installer metadata with correct URL, installer type, and
      minimum OS version.
- [ ] Given `retail-runtime-support.md`, when the install/update/uninstall sections
      are compared against the actual V3.23 implementation, then the docs accurately
      describe the shipped behavior.
- [ ] Given `platform-tiers.md`, when the file is reviewed, then `windows_retail`
      is listed as officially supported with V3.23 as the version that added
      distribution (runtime was V2.22).
- [ ] Given V2.21.md and V2.22.md, when they are reviewed, then they reference
      V3.23 for the remaining installer/distribution gap.
- [ ] Given the full V3.23 lifecycle, when a user installs → demos → updates →
      demos again → uninstalls (preserving evidence) → reinstalls, then all
      steps succeed and evidence is preserved.
