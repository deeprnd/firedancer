# V2.19.S3: Payment And Transfer Guard Workspace

**Status:** Backlog
**Epic:** #V2.19
**Parent roadmap item:** V2.19: Tickoni Terminal CaseOps UI
**Labels:** `story`, `payments`, `enhancement`

Render the V1.2-style failed payment, payout, retry, or transfer guard flow:
classification, beneficiary, rail, currency, retry, limit, risk, approval, and
evidence state.

## Product Outcome

Operators can inspect a payment exception and see whether Tickoni considers it
safe to propose, approval-required, blocked, or evidence-missing before any
money movement is possible.

## User Story

As a CaseOps operator, I want a payment guard workspace that shows all scope
and approval checks, so that I can review retry or transfer proposals without
trusting an agent summary alone.

## Scope

- In scope: failed payout summary (payer, rail, currency, amount, status),
  failure classification (reason, retryable flag, evidence refs), beneficiary
  and rail checks, currency and country scope, retry count vs. limit, daily
  beneficiary limit with remaining balance, risk flags, approval requirement
  with expiry, draft supplier message affordance, evidence reference display,
  and evidence refs to the audit/replay panel.
- Out of scope: payment retry execution, bank transfer initiation, processor
  API calls, new payment policy rules, or direct adapter calls.

## Preconditions And Assumptions

- Payment guard fixture data can represent allowed, approval-required,
  beneficiary-blocked, and evidence-missing states.
- The UI displays proposal or draft states only; execution remains outside this
  epic.
- The workspace renders inside the terminal shell from S1.

## Acceptance Criteria

- [ ] Given a retryable failed payout fixture, when the workspace renders, then
      beneficiary, rail, currency, retry count, daily limit, risk flags,
      approval state, and evidence refs are visible.
- [ ] Given an out-of-scope beneficiary fixture, when the workspace renders,
      then the decision is denied with direct action controls disabled.
- [ ] Given missing processor evidence, when the workspace renders, then the
      decision is `require_more_evidence` and the missing evidence is named.
- [ ] Given the `/save proposal` command, when the operator submits it, then
      the draft proposal state is recorded (if governed `tkapi` contract
      exists) or the command reports unavailable with a clear message.

### Conditional Acceptance

**Financial capability and policy**

- [ ] Payment scope is displayed across beneficiary, rail, currency, country,
      amount, retry count, risk flags, and approval requirement.

**Audit and replay**

- [ ] Evidence refs and replay status link to the audit/replay panel when
      available.

**Runtime topology and tile ownership**

- [ ] N/A - no topology changes.

**Model, tool, adapter, or execution boundary**

- [ ] Draft supplier messages and proposal states are display/review states;
      no UI path calls payment processors or adapters directly.

**CaseOps API or UI**

- [ ] Workspace data is loadable from a deterministic fixture or documented
      `tkapi` read response.

## Evidence Plan

- Demo or command: local UI flow using payment guard fixtures.
- Tests: render allowed-to-propose, approval-required, denied beneficiary, and
  evidence-missing states.
- Fixtures or samples: failed payout, out-of-scope beneficiary, missing
  processor record.
- Audit/replay evidence: evidence refs and replay status display fixture.
- Blocked-flow evidence: out-of-scope beneficiary fixture.
