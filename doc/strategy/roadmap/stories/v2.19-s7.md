# V2.19.S7: API Contracts, Fixtures, Screenshots, And Release Evidence

**Status:** Backlog
**Epic:** #V2.19
**Parent roadmap item:** V2.19: Tickoni Terminal CaseOps UI
**Labels:** `story`, `documentation`, `enhancement`

Define the minimum `tkapi` read/review contracts and evidence pack needed to
verify the terminal UI without weakening runtime boundaries.

## Product Outcome

Implementers, reviewers, and partners can see exactly which API shapes,
fixtures, screenshots, and tests prove the terminal behavior and no-bypass
guarantees.

## User Story

As a developer/operator, I want the UI contracts and evidence pack documented,
so that implementation can proceed without inventing policy, storage, adapter,
or execution semantics inside the frontend.

## Scope

- In scope: minimum read response examples for all terminal panels (shell,
  investment workbench, payment guard, impact view, audit/replay black box,
  capability/health panels), fixture file paths and schemas, screenshot
  checklist covering all panel types and states, blocked-flow examples,
  focused test commands, and contract notes for `tkapi`, `tkmetr`, and
  `tkdiag` — documenting that `tkapi` is the only UI boundary for case,
  evidence, proposal, approval, audit, replay, and health fanout.
- Out of scope: implementing new runtime endpoints, changing public contracts
  beyond documented read/review needs, or adding live external dependencies.

## Preconditions And Assumptions

- If an endpoint does not exist, this story documents the required contract
  before implementation work begins on any downstream story.
- Contract examples must preserve architecture boundaries and source-of-truth
  roles: Markdown is memory, DuckDB is analytics, TigerBeetle is ledger.
- S7 is a documentation and fixture story; it is the dependency that unlocks
  the implementation stories. Other stories should not begin until S7 has
  defined their required contract shapes.

## Acceptance Criteria

- [ ] Given this epic, when implementation starts, then every UI panel has a
      fixture or documented `tkapi` read response with source, freshness, and
      unavailable-state fields.
- [ ] Given a sensitive action affordance, when no approved runtime contract
      exists, then the UI contract marks the action disabled or proposal-only.
- [ ] Given release review, when evidence is collected, then screenshots,
      blocked-flow fixtures, and focused test commands are linked from this
      roadmap item.

### Conditional Acceptance

**Financial capability and policy**

- [ ] Contract examples carry policy version, outcome, reason, and relevant
      scope fields where policy applies.

**Audit and replay**

- [ ] Contract examples carry hashes, evidence refs, replay capsule id, status,
      and divergence fields where audit/replay applies.

**Runtime topology and tile ownership**

- [ ] Contract examples for health identify Tickoni tile IDs, links, producer,
      consumer, depth, reliability, and degraded state where available.

**Model, tool, adapter, or execution boundary**

- [ ] Contract examples include attribution and status only; no direct model,
      tool, adapter, or execution credentials appear in UI fixtures.

**CaseOps API or UI**

- [ ] `tkapi` is documented as the only UI boundary for case, evidence,
      proposal, approval, audit, replay, and health fanout.

## Evidence Plan

- Demo or command: documentation review plus local fixture-driven terminal run.
- Tests: schema/example validation and focused UI fixture tests.
- Fixtures or samples: investment, payment, impact, replay, capability,
  adapter, metric, and diagnostic examples.
- Audit/replay evidence: clean replay, tamper, stale capsule, and missing
  evidence examples.
- Blocked-flow evidence: restricted instrument, out-of-scope beneficiary,
  degraded adapter, unknown command, and unavailable impact examples.

## Quality Gate

- [ ] Focused tests for changed behavior pass.
- [ ] `just test-unit-tk` passes when Tickoni runtime code changes.
- [ ] `just test-integration-tk` passes when cross-tile, API, replay, adapter,
      or fixture behavior changes.
- [ ] `just test-demo-tk` or the story-specific demo command prints the required
      scenario when this story changes a demoable product flow.
- [ ] Documentation and roadmap status are updated when user-visible scope,
      non-goals, or evidence gates change.
