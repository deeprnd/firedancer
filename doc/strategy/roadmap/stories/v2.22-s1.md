# V2.22.S1: Platform support tier definitions

**Status:** Backlog
**Epic:** #[github-epic-issue]
**Parent roadmap item:** V2.22: Windows Retail Runtime Support
**Labels:** `story`, `platform`, `enhancement`

Define official runtime support tiers and their scope before any Windows
implementation hardens Linux-only assumptions.

## Product Outcome

Users and developers know whether their host is supported, which runtime tier
they are using, and which guarantees are unavailable before they run a
money-adjacent demo on Windows.

## User Story

As a developer-community evaluator, I want Tickoni to name the supported
runtime tier for my Windows machine, so that I can run the right demo path
without assuming Linux-equivalent performance or isolation.

## Scope

- In scope: define tier language for Windows, map workflows to tiers, specify
  degraded-guarantee visibility rules.
- Out of scope: Windows implementation decisions (separate stories),
  Firedancer porting (S4), installer design (S4).

## Preconditions And Assumptions

- V2.14 established the Linux full-runtime tier with Firedancer process and
  shared-memory topology.
- Linux remains the default high-throughput tier unless a separate decision
  approves native parity.
- V2.21 (macOS) defines the tier language pattern; V2.22 adapts it for Windows.

## Acceptance Criteria

- [ ] Given a host OS and architecture, when the user checks tier definitions,
      then the output identifies Linux full-runtime, Windows retail runtime,
      container/WSL2/VM-assisted mode, or unsupported.
- [ ] Given a supported tier, when the user selects a workflow, then the tier
      explicitly states which workflows are supported (build-only,
      doctor-only, deterministic paper demo, CaseOps review, replay proof,
      sandbox adapter substitute, full Linux tile runtime) and which are not.
- [ ] Given degraded guarantees (performance, sandboxing, networking, shared
      memory, execution), when the runtime reports tier status, then the
      degradation is visible in CLI, CaseOps, audit, replay, and docs.

## Evidence Plan

- Demo or command: `tickoni --version` or `tickoni doctor` output on a
  supported Windows host identifying tier and OS.
- Tests: N/A - language/definition story; documentation review is the verification.
- Fixtures or samples: Tier definition document or struct definitions.
- Audit/replay evidence: N/A - tier metadata feeds into S3/S7.
- Blocked-flow evidence: N/A.

## Quality Gate

- [ ] Tier definitions are documented or codified before the Windows
      implementation story starts.
- [ ] No story in this epic can proceed with an implicit WSL2, container,
      or VM choice without an explicit tier decision.
- [ ] Documentation and roadmap status are updated when tier definitions change.
