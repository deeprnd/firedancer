# V2.19.S6: Capability, Adapter, Metric, And Diagnostic Panels

**Status:** Backlog
**Epic:** #V2.19
**Parent roadmap item:** V2.19: Tickoni Terminal CaseOps UI
**Labels:** `story`, `platform`, `enhancement`

Show the operational control plane: capability catalog, adapter status,
approval paths, aggregate limits, queue health, tile health, API status,
metrics, diagnostics, and degraded-state explanations.

## Product Outcome

Runtime owners and reviewers can see whether the governed harness itself is
healthy, which capabilities are available, which adapters are degraded, and
which policy or approval paths apply.

## User Story

As a runtime owner, I want capability and health panels in the terminal, so
that I can distinguish a policy denial from an unavailable adapter, unhealthy
queue, or diagnostic failure.

## Scope

- In scope: capability catalog cards or tables (action classes, scope
  dimensions, policy versions), adapter pings and status (healthy, degraded,
  unavailable), approval paths (require_approval paths, approval expiry
  windows), aggregate limits (daily notional remaining, monthly remaining,
  per-beneficiary remaining), tile status (tickoni tile IDs, not Solana
  validator identities), queue depth and backpressure state (producer, consumer,
  depth, reliability, overrun behavior), API health, metrics summary,
  diagnostic indicators, and degraded badges with explanation text.
- Out of scope: changing capability definitions, adapter manifests, metrics
  schemas, diagnostics ownership, or sandbox policy.

## Preconditions And Assumptions

- Health and capability data is sourced from fixture-compatible `tkapi`,
  `tkmetr`, and `tkdiag` surfaces.
- Firedancer reuse is limited to generic substrate patterns documented in
  architecture and tile-topology docs.
- The panels render inside the terminal shell from S1.
- Firedancer infrastructure is referenced generically (queues, topology,
  workspaces, metrics, diagnostics) — no Solana validator tile IDs, RPC
  schemas, or validator-specific concepts are exposed.

## Acceptance Criteria

- [ ] Given healthy runtime fixture data, when the panels render, then each
      tile, queue, adapter, capability family, and API surface shows an
      understandable healthy state.
- [ ] Given degraded adapter fixture data, when the panels render, then the
      adapter is marked degraded and related action controls are blocked or
      unavailable.
- [ ] Given queue backpressure fixture data, when the panels render, then the
      affected link, producer, consumer, depth, and overrun/backpressure state
      are visible.

### Conditional Acceptance

**Financial capability and policy**

- [ ] Capability catalog displays action classes and scope dimensions from
      documented capability data; it does not define new policy.

**Audit and replay**

- [ ] N/A - health panels do not alter audit or replay records.

**Runtime topology and tile ownership**

- [ ] Topology display is read-only and names Tickoni tile IDs only; no Solana
      validator tile identities are exposed as product concepts.

**Model, tool, adapter, or execution boundary**

- [ ] Adapter and model health are display-only; no direct provider or adapter
      calls are introduced.

**CaseOps API or UI**

- [ ] Metrics and diagnostics are loaded from `tkapi`, `tkmetr`, `tkdiag`, or
      deterministic fixtures, not from raw process scraping in UI code.

## Evidence Plan

- Demo or command: local UI flow using healthy, degraded adapter, and
  backpressure fixtures.
- Tests: render healthy, degraded, and backpressure states.
- Fixtures or samples: capability catalog, adapter status, queue health,
  diagnostic sample.
- Audit/replay evidence: N/A - operational health only.
- Blocked-flow evidence: degraded adapter fixture.
