# V2.23.S1: Release pipeline — per-platform/per-architecture tarballs, SHA256 checksums, winget manifests

**Status:** Backlog
**Epic:** #[github-epic-issue] (V2.23)
**Parent roadmap item:** V2.23: Distribute a Runnable Tickoni Package with Installation, Verification, and Update Flow
**Labels:** `type/story`, `area/operations`, `type/feature`

<!-- One sentence: the independently verifiable deliverable. -->

CI produces per-platform (Linux, macOS, Windows), per-architecture (x86_64, ARM64)
tarballs containing `tickoni` and `tickoni-supervisor` binaries from `zig-out/bin/`,
publishes SHA256 checksums for each artifact, and generates winget manifests for
Windows per-user distribution.

## Product Outcome

A CI run on any supported platform/combination produces a versioned release
artifact that a user can download and verify before installing. The artifact
carries the Tickoni version, OS, architecture, runtime tier, and isolation tier
in its filename and metadata.

## User Story

As a partner reviewer or developer-community evaluator, I can download a
pre-built Tickoni tarball for my platform, verify its SHA256 checksum against
published hashes, and be confident the binary has not been tampered with before
running the installer.

As a runtime owner, I can push a new version and have CI automatically produce
all platform/architecture artifacts with checksums and winget manifests without
manual intervention.

## Scope

- In scope:
  - CI workflow triggers on release or tag to build per-platform/per-arch tarballs
    from `zig-out/bin/tickoni` and `zig-out/bin/tickoni-supervisor`.
  - Each tarball is named with version, OS, and architecture (e.g.
    `tickoni-2.23.0-macos-arm64.tar.gz`).
  - A `checksums.txt` (SHA256) file is published alongside each tarball.
  - Winget manifest (`.yaml`) is generated for each Windows release.
  - No `.pkg`, `.deb`, `.rpm`, or Homebrew formula at this stage.
  - No code signing or Sigstore — checksums only.
  - No automatic version tagging; release workflow is triggered manually or
    by a tag push.

- Out of scope:
  - macOS `.pkg` or Homebrew tap.
  - Linux `.deb` or `.rpm` packaging.
  - Code-signing infrastructure (Sigstore, GPG, minisign).
  - Automatic self-update in the runtime.
  - Cross-platform single-binary distribution.
  - Docker/container image publishing.
  - Windows MSI installer.

## Preconditions And Assumptions

- V2.21.S4 and V2.22.S4 produce working `zig-out/bin/tickoni` and
  `zig-out/bin/tickoni-supervisor` binaries for all supported platforms and
  architectures.
- `retail-runtime-support.md` already documents the install layout
  (`~/.tickoni/bin/`) and the expected binary names.
- The runtime does not need broker, payment, crypto, or live model-provider
  credentials to build — all dependencies are build-time.
- Users are responsible for verifying checksums before running installers.

## Acceptance Criteria

- [ ] Given a release tag push, when the CI release workflow runs, then tarballs
      are produced for all supported platform/architecture combinations:
      `linux-x86_64`, `macos-arm64`, `macos-x86_64`, `windows-x86_64`,
      `windows-arm64`.
- [ ] Given a release tarball, when a user runs `sha256sum` on it and compares
      against the published `checksums.txt`, then the hash matches and the user
      can verify integrity.
- [ ] Given a Windows release, when the CI produces assets, then a winget
      manifest (`tickoni.yaml`) is generated per version with the correct
      installer URL, installer type (tarball), and minimum OS version.
- [ ] Given an unsupported platform/architecture (e.g. `windows-arm32`), when
      the release workflow runs, then no tarball is produced and the user sees
      an explicit error in CI logs.
- [ ] Given a release tarball, when it is extracted, then `tickoni` and
      `tickoni-supervisor` are present and executable without requiring `sudo`.
