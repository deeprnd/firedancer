Analysis
    
    The audit finding is correct. The same tile identity (TileId) is independently mapped in four places, with no shared source of truth:
    
    Layer 1 -- supervisor.zig:134-148 (thread-mode start):
    
    handles[0] = spawn(tiles_mod.runIngest, ...)
    handles[1] = spawn(tiles_mod.runNormalize, ...)
    handles[2] = spawn(tiles_mod.runDedupe, ...)
    ...
    
    Index-based. Assumes topo.tiles[0] == runIngest, topo.tiles[1] == runNormalize, etc. Breaks if you reorder, add, or remove tiles without changing the app layer.
    
    Layer 2 -- supervisor.zig:372-393 (snapshotProcessMetrics):
    
    if (id == "tkings") snap.produced = read(cnc, 0);
    else if (id == "tknorm") { snap.normalized = read(cnc, 0); snap.invalid = read(cnc, 1); }
    ...
    
    String-based. Hardcodes which counters belong to which tile, and what field names on ProcessMetricSnapshot they map to. The field names (produced, normalized, invalid, duplicates, allowed, denied, audited) are payment-pipeline semantics leaking into a supposedly generic supervisor.
    
    Layer 3 -- tile_main.zig:34-73 (runPipelineStage):
    
    if (id == "tkings") runIngestProcess(...)
    else if (id == "tknorm") runNormalizeProcess(...)
    ...
    
    Another independent if/else chain on the same strings, mapping to different run functions.
    
    Layer 4 (implicit) -- process.zig:60,87-88,118,163-164,191 (counter indices):
    
    appCounterWrite(cnc, 0, produced);  // tkings
    appCounterWrite(cnc, 0, normalized); appCounterWrite(cnc, 1, invalid);  // tknorm
    appCounterWrite(cnc, 0, duplicates);  // tkdedu
    appCounterWrite(cnc, 0, allowed); appCounterWrite(cnc, 1, denied);  // tkpoly
    appCounterWrite(cnc, 0, audited);  // tkaudt
    
    Counter indices are written by tiles but read by supervisor.zig. Nobody owns the mapping. Counter index 0 means "produced" in tkings, "normalized" in tknorm, "duplicates" in tkdedu, "allowed" in tkpoly, "audited" in tkaudt.
    
    The fundamental flaw: There is no one data structure that answers: "given a TileId, what does this tile do?" Instead, the answer is computed independently by four code paths, each of which can diverge.
    

Option evaluation
    
    Option A: Static comptime table in tiles/mod.zig
    
    A single comptime { ... } block builds a sorted lookup table at compile time:
    
    zig
    pub const TileRegistry = struct {
        entries: [MAX_TILES]TileEntry,
        len: usize,
    
        pub const TileEntry = struct {
            tile_id: TileId,
            /// For thread-mode: the spawn target.
            run_fn: const fn (PaymentPipelineState) anyerror!void,
            /// For process-mode: the runPipelineStage dispatch tag.
            process_fn: ?*const fn(...) anyerror!void = null,
            /// Counter schema for this tile in process mode.
            /// { num_counters, [counter_names...] }
            counter_schema: CounterSchema = .{ .count = 0, .names = undefined },
        };
        // ... binary search lookup by TileId
    };
    
    
    Pros: Compile-time validated -- every tile in the topology must be registered or compilation fails. Zero runtime overhead. Single place to add a tile.
    
    Cons: Still requires the app layer (supervisor, tile_main) to have visibility into tile registry internals. The counter_schema names field requires careful management. Adding a new pipeline topologies requires updating every pipeline's registry.
    
    Best for: Projects where the tile set is stable and small.
    
    Option B: Runtime registry module (recommended)
    
    Create src/app/tickoni/tile_registry.zig with:
    
    1. A TileRegistry struct that the app layer initializes at startup:
       zig
       pub const TileRegistry = struct {
           entries: [16]TileDescriptor,  // enough for Phase 0+1
           len: usize,
    
           pub fn init(...) TileRegistry { ... }
           pub fn findByIdx(topo: *const Topology, i: usize) *const TileEntry { ... }
           pub fn findById(id: TileId) *const TileEntry { ... }
           pub fn validate(topo: *const Topology) void { ... }
       };
       
    
    2. Registration happens once in the app module:
       zig
       pub fn buildRegistry() TileRegistry {
           var reg = TileRegistry{};
           reg.append(.{ .id = TileId.parse("tkings"), ... });
           reg.append(.{ .id = TileId.parse("tknorm"), ... });
           // ... all 8 Phase 0 tiles
           return reg;
       }
       
    
    3. supervisor.zig reads from it instead of index-based spawn and string-based metrics:
       zig
       // Before: handles[0] = spawn(tiles_mod.runIngest, ...)
       // After:
       const entry = registry.findByIdx(i);
       handles[i].thread = try std.Thread.spawn(.{}, entry.run_fn, .{state});
       
    
    4. tile_main.zig reads from it instead of string dispatch:
       zig
       // Before: if (std.mem.eql(u8, id, "tkings")) runIngestProcess(...)
       // After:
       const entry = registry.findById(spec.tile_id);
       entry.process_fn(...)
       
    
    5. snapshotProcessMetrics reads from it -- the registry owns the counter schema:
       zig
       const entry = registry.findById(tile.id);
       for (entry.counter_schema, 0..) |counter, ci| {
           const value = rt.cnc_counters.appCounterRead(cnc, ci);
           // Update the appropriate field on ProcessMetricSnapshot
       }
       
    
    Pros: Single source of truth for all three consumers. Adding a new tile is one registration. Compile-time topology validation in topologies.zig plus runtime registry validation (every topo tile must exist in registry). Easy to unit test the registry in isolation.
    
    Cons: More code. Runtime lookup cost (negligible -- this is init/wait path, not hot loop). New module to maintain.
    
    Option C: Hybrid -- comptime enum + runtime dispatch table
    
    Use a comptime enum for tile IDs and a runtime lookup table built from it:
    
    zig
    pub const TileKind = enum(u8) {
        tkings, tknorm, tkdedu, tkpoly, tkaudt, tkrepl, tkmetr, tkdiag,
    
        pub const count: u8 = 8;
    
        // Comptime-generated lookup: TileId -> TileKind
        pub fn fromSlice(id: []const u8) ?TileKind {
            comptime var i: u8 = 0;
            while (i < count) : (i += 1) {
                const name = std.meta.tagName(@typeInfo(TileKind).Enum.fields[@intCast(i)]);
                if (std.mem.eql(u8, id, name)) return @as(TileKind, @enumFromInt(i));
            }
            return null;
        }
    };
    
    // Runtime dispatch table keyed by TileKind:
    const RunFnTable = struct {
        entries: [TileKind.count]RunFn,
        pub fn init() RunFnTable { ... }
    };
    
    
    Pros: TileKind enum is a first-class type. No string comparisons anywhere in the hot path. The fromSlice comptime generation is DRY. Easy to add new variants -- just add an enum field.
    
    Cons: TileKind name != TileId slice in general (TileId is "tkings" but the enum field might be "ingest"). The std.meta.tagName approach requires enum fields to be lowercase snake_case or kebab-case, not the 6-char tile ID format. You'd need explicit name mappings anyway.
    
    Best for: When the hot path (inside the tile loop) needs fast dispatch. But here the registry is only used on init/wait, not in the tile's inner loop.
    
    
    
    Recommendation: Option B, with a specific refinement
    
    Why Option B is the right fit for Tickoni right now:
    
    1. The registry is an init/wait-time concern, not a hot path concern. Thread-mode spawn and process-mode dispatch happen once per pipeline lifecycle. Metrics snapshot is called periodically but only reads -- no inner-loop latency impact. A runtime lookup is fine.
    
    2. Zig doesn't have a clean way to store function pointers in comptime arrays. Option A would require workarounds (boxing function pointers, type erasure) that add complexity without real benefit.
    
    3. Option C's comptime enum approach is clever but over-engineered. The string comparison overhead in tile_main.zig is negligible (it runs once at tile boot, not per-message). The real problem isn't string comparisons -- it's that the comparison result is duplicated in three unrelated places.
    
    4. Option B scales to future topologies. When investmentWorkflow() becomes runnable, the registry can grow from 8 to 14 entries without touching supervisor.zig or tile_main.zig logic.
    
    The specific refinement: Don't overcomplicate the registry schema. The current code has a small, fixed set of concerns per tile. Keep the registry simple:
    
    zig
    // tile_registry.zig
    
    pub const TileEntry = struct {
        id: TileId,
        name: []const u8,
        run_fn_thread: const fn (PaymentPipelineState) anyerror!void,
        /// Process-mode dispatch: what to call for this tile's pipeline stage.
        process_stage: ?*const fn(wksp, spec, cnc, alloc) anyerror!void = null,
        /// Counter schema: which indices this tile writes in process mode.
        /// Each entry is { index, counter_name }.
        /// Empty schema (count = 0) means this tile writes no counters.
        counter_schema: CounterSchema = .{ .count = 0 },
    };
    
    pub const CounterSchema = struct {
        count: usize,
        entries: [8]struct { index: usize, name: []const u8 },
    };
    
    
    This replaces:
    - supervisor.zig:134-148 -- replace 15 hardcoded spawn calls with a single loop: for (handles, 0..) |*h, i| { const entry = registry.findById(topo.tiles[i].id); h.thread = try spawn(.{}, entry.run_fn_thread, .{state}); }
    - supervisor.zig:372-393 -- replace the if/else chain with a loop over entry.counter_schema entries, reading each counter index and updating the snapshot field by name.
    - tile_main.zig:34-73 -- replace the if/else chain with a single registry.findById(spec.tile_id).process_stage(...).
    
    Verification strategy:
    1. Write tile_registry.zig with all 8 Phase 0 tiles registered.
    2. Add a test: registry.validate(topo) asserts that every tile in the topology is registered and no registered tile is missing from the topology.
    3. Rewrite supervisor.zig's start and metrics paths.
    4. Rewrite tile_main.zig's dispatch.
    5. Run zig build test -- existing tests should pass unchanged because the behavioral contract is identical.
    6. Add a unit test that verifies the registry's counter schema matches the actual counter writes in process.zig (compile-time check: the registry entry's schema count must match the actual number of appCounterWrite calls for each tile).
    
    What to defer:
    - Counter name field names on ProcessMetricSnapshot: The current snapshot struct has payment-specific field names (produced, normalized, invalid). Making it fully generic (any counter name) would require either a generic key-value map (overkill for 7 fields) or changing snapshot to use a flexible struct. Defer this -- the fields are fine for Phase 0, and the registry just maps them instead of hardcoding the mapping.
    - Tile lifecycle hooks (privileged_init, unprivileged_init): These are in tile_process.zig but currently not used by the payment pipeline tiles. Not part of the current duplication problem.
    - Multi-pipeline support: When there are two different pipelines (payment + investment), the registry can be parameterized. Not worth optimizing for today.
    
    Firedancer uses a three-layer indirection, not a flat dispatch table:
        
        
        tile name string → fdctl_tile_run() → TILES[] lookup → fd_topo_run_tile_t struct

        Layer 2: The dispatcher (fdctl_tile_run() in fd_boot.c:18-25)

        fd_topo_run_tile_t
        fdctl_tile_run( fd_topo_tile_t const * tile ) {
          for( ulong i=0UL; TILES[ i ]; i++ ) {
            if( !strcmp( tile->name, TILES[ i ]->name ) ) return *TILES[ i ];
          }
          FD_LOG_ERR(( "tile %s not found", tile->name ));
          return (fd_topo_run_tile_t){0};

        This is the same linear string-comparison dispatch the audit flagged. But Firedancer tolerates it because:
        
        1. It runs once at boot, never in a hot path (tiles are already launched by then)
        2. It's the single point that answers "what does this tile do?"
        3. Every other consumer goes through it
        
        Layer 3: Where it's consumed (4 call sites)
        
        
        fd_topo_run.c:329   run_tile_thread   →  tile_run(tile)
        fd_obj_callbacks.c:247,264,281          tile_footprint/tile_loose/tile_align
        run.c:304-300                               execve_tile per tile in topo
        run1.c:49                                 tile_run(args->tile)
        
        
        The key distinction from Tickoni: Firedancer's fdctl_tile_run() is the canonical single function that every consumer calls. Tickoni has three consumers that each write their own if/else chain instead of calling one canonical function.
        
        
        
        Firedancer's fd_topo_run_tile_t struct (the registry entry)

        Every tile owns its struct. The harness reads it. That's it. The struct has everything any consumer needs: the name for lookup, the footprint/align for memory planning, the init/run callbacks for lifecycle, the seccomp/fd lists for sandboxing.
        
        Firedancer doesn't have a separate "metrics field" concept. Each tile's fd_topo_run_tile_t struct has a .name field. The supervisor (main_pid_namespace in run.c) identifies tiles by name when they crash (child_names[ i ]). Metrics are stored per-tile in shared memory (tile->metrics) and are identified by the tile's position in the topology array (topo->tiles[ tile_idx ].metrics), not by string matching at snapshot time.
        
        
        
        Where Firedancer does NOT have the same problem as Tickoni
        
        Problem: Thread-mode spawn
        Firedancer: fd_topo_run_tile() calls tile_run->run(topo, tile) once per tile in
          fd_topo_run_single_process() loop over topo->tiles — no per-tile indexing needed
        Tickoni: handles[0] = spawn(runIngest), handles[1] = spawn(runNormalize) — hardcoded
          index-to-tile mapping
        ────────────────────────────────────────
        Problem: Process-mode dispatch
        Firedancer: run1.c calls fdctl_tile_run(tile) which does one string lookup → returns struct →
          harness calls struct.run(topo, tile)
        Tickoni: tile_main.zig has its own if (id == "tkings") chain
        ────────────────────────────────────────
        Problem: Metrics snapshot
        Firedancer: main_pid_namespace identifies crashed tiles by child_names[i] (copied from
          tile->name at spawn time); metrics accessed via topo->tiles[tile_idx].metrics
        Tickoni: snapshotProcessMetrics reads each cnc and does if (id == "tkings") to decide which
          snapshot field to fill
        
        Firedancer solves the first two by having one canonical lookup (fdctl_tile_run()) that the harness uses for both lifecycle and process dispatch. It solves the third by never snapshotting tile metrics by name — the metrics array is indexed by topology position, not looked up.
        
        
        
        What Firedancer does that's relevant to Tickoni
        
        1. Tile-owned registration
        
        Each tile's .c file defines its own fd_tile_* struct. The module is the sole owner of what its tile does. No one else has a copy of that information. This is the pattern Tickoni should follow.
        
        2. Null-terminated lookup array
        
        TILES[] is null-terminated, so you don't need a separate count. The loop for(; TILES[i]; i++) is simple and correct.
        
        3. Single dispatcher function
        
        fdctl_tile_run() is the one and only place that maps a tile name to its capabilities. Everything calls it. Tickoni has three places that map a tile name to its behavior, and they're independent.
        
        4. No separate metrics field mapping
        
        Firedancer's metrics are position-indexed (topo->tiles[idx].metrics). The supervisor never does string comparison to find metrics. Tickoni's snapshotProcessMetrics does string comparison AND maps to payment-specific field names.
        
        5. Build-time TILES[] population
        
        The TILES[] array is populated manually in each binary's main.c (fdctl, firedancer, firedancer-dev). Each binary lists only the tiles it supports. This is not linker-synthesized — it's a hand-written array. Tickoni's topologies.zig already has the static tile arrays (payment_tiles[]), which is the equivalent.
        
        
        
        What this means for Tickoni
        
        Firedancer's pattern is basically what I recommended as Option B (runtime registry), but with a crucial difference in how metrics are handled:
        
        Firedancer metrics are position-indexed, not name-matched.
        
        In Firedancer:
        - fd_topo_run_tile() calls fd_metrics_register(tile->metrics) with a pointer into the tile's pre-allocated metrics block
        - The supervisor identifies tiles by position in the topology array
        - No string comparison needed at metrics-read time
        
        In Tickoni:
        - snapshotProcessMetrics() matches tile names as strings, then decides which counters to read and where to put them
        - Counter indices (0, 1) are payment-domain semantics (index 0 = "produced" in tkings, "normalized" in tknorm)
        - The registry would need to own the counter schema mapping
        
        The Firedancer-inspired approach for Tickoni:
        
        zig
        // tile_registry.zig
        
        pub const TileRegistryEntry = struct {
            id: TileId,
            /// Thread-mode run function (for startPaymentPipeline thread mode)
            run_fn: const fn (PaymentPipelineState) anyerror!void,
            /// Process-mode: the decision logic to run for this tile
            process_fn: ?*const fn(wksp, spec, cnc, alloc) anyerror!void = null,
            /// For process-mode metrics: which cnc app-counter indices this tile writes
            /// and what they mean. Index 0 is always the primary output counter.
            counter_schema: [8]struct { idx: usize, name: []const u8 } = .{.{.idx=0,.name="n/a"}} ** 8,
            counter_count: usize = 0,
        };
        
        pub const TileRegistry = struct {
            entries: [16]TileRegistryEntry,
            len: usize,
            
            pub fn findById(self: const TileRegistry, id: TileId) ?const TileRegistryEntry { ... }
            pub fn findByIdx(self: const TileRegistry, i: usize) ?const TileRegistryEntry { ... }
            pub fn validate(self: *const TileRegistry, topo: *const Topology) void { ... }
        };
        
        
        Key design decisions where Firedancer informs Tickoni:
        
        1. Tile-own registration: Each tile module (ingest.zig, normalize.zig, etc.) registers its own entry. The registry init function in mod.zig calls register(.ingest, ...) from each module. No other module has a copy of what ingest does.
        
        2. Single dispatcher: One registry.findById(id) call replaces all three if/else chains.
        
        3. Counter schema ownership: The registry owns which counter index means what for each tile. snapshotProcessMetrics iterates the schema instead of matching strings.
        
        4. Position-based handle mapping: handles[i] stays, but the registry maps topo.tiles[i] → registry entry, so the supervisor doesn't need to know that "index 3 is policy."
        
        5. No metrics-by-name at runtime: Firedancer avoids this entirely by using position indexing. Tickoni could do the same — snapshotProcessMetrics reads counter indices from the registry entry for topo.tiles[i], no string matching.
        
        What Firedancer does differently (and why it's not directly portable):
        
        - Firedancer's fd_topo_run_tile_t struct includes seccomp/FD lists, rlimits, footprint/align, init/run callbacks — it's the complete tile capability descriptor. Tickoni's registry can be lighter since sandboxing is simpler and footprint is managed differently.
        - Firedancer's stem_run is a generic run loop that tiles plug into. Tickoni tiles have custom loops, so the registry's run_fn is per-tile, not a shared template.
        - Firedancer reads metrics from a shared memory array indexed by position. Tickoni's counter schema lives in a separate cnc app-defined region, so it needs the schema mapping.
        
        The core insight: Firedancer's fdctl_tile_run() + TILES[] is the same pattern I described — one registry, multiple consumers. The reason Tickoni needs it is because Firedancer has exactly one place that needs tile identity → capabilities, and Tickoni has three places that each re-implement the mapping.
