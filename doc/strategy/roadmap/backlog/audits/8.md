Here's a thorough comparison of how Firedancer handles stuck/blocked tiles vs. Tickoni's current tile_process lifecycle:
    
    Current Tickoni Problem
    
    In tile_process.zig lines 69-99:
    
    
    heartbeat(cnc, ...)           // first heartbeat (line 69)
    signal(cnc, RUN)              // signal RUN (line 78)
    work(...)                     // TILE-SPECIFIC WORK (line 80) -- BLOCKS HERE
    while (true) {                // heartbeat/halt loop (line 86)
        signalQuery(cnc)          // check for HALT
        heartbeat(cnc, ...)       // heartbeat
    }
    
    
    The problem: work() runs synchronously and is completely opaque to the generic lifecycle. No heartbeat. No halt check. If work() blocks in a consume() or publish() call, the tile looks dead to the supervisor. The tile-specific loops (process.zig) each have if (halted(cnc)) break; checks, but only between iterations -- not mid-await.
    
    Firedancer's Three-Layer Defense
    
    Layer 1: Process-level isolation (the hard boundary)
    
    run.c (lines 394-439): The Firedancer supervisor (main_pid_namespace) runs in a PID namespace. It spawns all tiles as child processes and watches them with poll() on per-tile pipefds + wait4(-1, ..., WNOHANG). 
    
    If any child process dies, the supervisor immediately:
    - Logs which tile died
    - Terminates all remaining children
    - Exits with appropriate code
    
    This means a stuck tile won't bring down the entire system indefinitely -- it just hangs until someone kills the supervisor, at which point everything dies.
    
    run1.c (line 50): Each tile runs via fd_topo_run_tile() in its own clone'd process. The fd_topo_run_tile function (lines 49-140) has a single exit path: either the tile's run() callback returns, or it crashes.
    
    Layer 2: Stem's SHOULD_SHUTDOWN callback (the soft boundary)
    
    fd_stem.c (line 393): At the top of every stem loop iteration:
    
    c
    #ifdef STEM_CALLBACK_SHOULD_SHUTDOWN
        if( FD_UNLIKELY( STEM_CALLBACK_SHOULD_SHUTDOWN( ctx ) ) ) break;
    #endif
    
    
    This is called every iteration of the stem's for(;;) loop (line 390), which means:
    - After processing a fragment
    - After before_credit work
    - After after_credit work
    - During backpressure spin (via housekeeping)
    
    Tiles define this callback:
    - fd_genesi_tile.c (line 598): #define STEM_CALLBACK_SHOULD_SHUTDOWN should_shutdown
    - fd_bundle_tile.c: does NOT define it (bundle relies on stem's inherent loop granularity)
    
    The should_shutdown function typically checks an fseq-based flag that the supervisor writes to -- this is Firedancer's analog to Tickoni's CNC signal mechanism, but it's checked at the stem loop top, not buried inside tile-specific logic.
    
    Layer 3: Metrics-based health monitoring (the external boundary)
    
    fd_stem.c (lines 427): During housekeeping events:
    
    c
    FD_MGAUGE_SET( TILE, HEARTBEAT_TIMESTAMP_NANOS, (ulong)fd_log_wallclock() );
    
    
    This writes to shared memory metrics every housekeeping interval (configurable via STEM_LAZY, bundle uses 10e6 = 10ms).
    
    ready.c (lines 25-39): The Firedancer ready command polls fd_metrics_tile(tile->metrics)[FD_METRICS_GAUGE_TILE_STATUS_OFF] in a loop. Status 1 = running, 2 = shut down. If a tile's metrics stop updating, the ready check will hang forever -- but this is the observer problem, not the handler problem.
    
    fd_gui.c (line 509): The GUI reads tile_metrics[...][HEARTBEAT_TIMESTAMP_NANOS] and displays it. If it stops advancing, operators know a tile is stuck.
    
    Key Architectural Differences
    
    Aspect: Tile lifecycle
    Firedancer: Stem loop with callbacks
    Tickoni (current): Synchronous work() call
    ────────────────────────────────────────
    Aspect: Shutdown check
    Firedancer: SHOULD_SHUTDOWN at stem loop top
    Tickoni (current): Tile-specific halted(cnc) between iterations only
    ────────────────────────────────────────
    Aspect: Heartbeat
    Firedancer: Inside stem housekeeping (periodic)
    Tickoni (current): Before work() + after work() completes
    ────────────────────────────────────────
    Aspect: Process model
    Firedancer: clone() per tile, PID namespace
    Tickoni (current): exec self into per-tile process
    ────────────────────────────────────────
    Aspect: Supervisor detection
    Firedancer: wait4() + poll() for process death
    Tickoni (current): CNC signal state + metrics heartbeat
    ────────────────────────────────────────
    Aspect: Backpressure handling
    Firedancer: Stem loop continues iterating during backpressure
      (spin+continue)
    Tickoni (current): Tile blocks in consume()/publish()
    
    The Critical Gap
    
    Firedancer's stem loop has the property that every iteration checks shutdown conditions before doing meaningful work. The stem's for(;;) loop structure is:
    
    c
    for(;;) {
        // 1. Check SHOULD_SHUTDOWN (tile-defined)
        // 2. Housekeeping (metrics, credits, flow control) -- periodic
        // 3. before_credit callback
        // 4. Check backpressure (spin, then continue)
        // 5. after_credit callback
        // 6. Poll for fragments, process them
        // 7. after_frag callback
    }
    
Tickoni's tile_process.run() collapses this into:
    
    
    work()  // everything happens here -- no loop, no interleaving
    
    
    The tile-specific functions (runIngestProcess, runNormalizeProcess, etc.) have their own while loops with halted(cnc) checks, but:
    1. No heartbeat during the loop -- the supervisor sees stale heartbeats
    2. No check during blocking I/O -- if consume() blocks indefinitely, halted() is never reached
    
What prevents Tickoni from reusing the harness as-is
    
    The harness is generic but tightly coupled to Firedancer's validator binary, not to Solana:
    
    1. fd_topo_t / fd_topo_tile_t structures contain fields like agave_affinity_cnt, is_agave, shredstream, quic_listen_port, pack_execle, replay_in — these are Solana/Firedancer validator topology fields. Tickoni's topology (launch_spec.zig) is simpler and finance-oriented.
    
    2. fdctl dependency: The harness expects the Firedancer CLI tool (fdctl) for configuration, topology loading, and coordination. Tickoni's supervisor is a standalone Zig binary.
    
    3. fd_topob.c topology builder: Contains reserve_agave_cores and Agave core pinning logic. Generic in principle but the topology structure itself is Solana-shaped.
    
    4. The stem callback interface is generic but assumes the Firedancer metrics framework (FD_MGAUGE_SET, FD_MCNT_SET) and metrics generated for Solana tile IDs.
    
    5. Single-binary coupling: Firedancer runs all tiles as threads or forked children of a single fd binary. Tickoni uses self-exec (execve) of its own binary per tile, which is architecturally different but cleaner for a finance-oriented runtime.
    
    Verdict
    
    The Firedancer harness is generic infrastructure that happens to be embedded in a Solana validator. The primitives (cnc, mcache, dcache, fseq, wksp, stem, sandbox) are all Solana-free. The coupling that prevents Tickoni from reusing it as-is is:
    
    - Firedancer validator topology structures (fd_topo_tile_t with is_agave, shred fields, etc.)
    - fdctl CLI dependency
    - Firedancer metrics framework (generated per-Solana-tile)
    - Single-binary execution model
    
The Firedancer harness has a clear contract. Here's what it expects from a tile, and whether Tickoni can conform to each piece.
    
    The Tile Contract (4 layers)
    
    Layer 1: Launch — fd_topo_run_tile_t struct
    
    This is a C struct passed to fd_topo_run_tile():
    
    c
    typedef struct fd_topo_run_tile_t {
      const char*               name;
      ulong                     scratch_align;
      ulong                     scratch_footprint;
      ulong                     loose_footprint;
      void (privileged_init)(fd_topo_t, fd_topo_tile_t*);
      void (unprivileged_init)(fd_topo_t, fd_topo_tile_t*);
      void (run)(fd_topo_t, fd_topo_tile_t*);
      void (populate_allowed_seccomp)(fd_topo_t, fd_topo_tile_t*, ...);
      int (populate_allowed_fds)(fd_topo_t, fd_topo_tile_t*, ...);
      uint rlimit_file_cnt;
      // etc.
    } fd_topo_run_tile_t;
    
    
    Tickoni's view: Tickoni already has the equivalent — tile_main.zig calls WorkFn callbacks (privileged_init, unprivileged_init, work) that match this signature. The tile_process.zig lifecycle is already a parallel implementation of fd_topo_run_tile() — it joins workspaces, calls init callbacks, then calls work in a loop with heartbeat/halt checks. The callback signatures already match.
    
    Verdict: ✅ Adaptable. Tickoni already has the callback pattern. The bridge just needs to expose the same symbols.

Layer 2: Execution — the run callback
    
    fd_topo_run_tile() does (lines 49-140 of fd_topo_run.c):
    
    
    1. fd_topo_join_tile_workspaces(topo, tile)   // map workspaces
    2. tile_run->privileged_init(topo, tile)       // pre-sandbox init
    3. Sandbox setup (seccomp, fds, UID/GID)
    4. fd_topo_fill_tile(topo, tile)               // join shared memory (mcache/dcache/cnc)
    5. tile_run->unprivileged_init(topo, tile)     // post-sandbox init
    6. tile_run->run(topo, tile)                   // main loop
    
    
    Then Tickoni's tile_process.run() does the same sequence in different order:
    
    1. join workspaces (wksp)
    2. privileged_init (tile's callback)
    3. sandbox (via TK_SANDBOX_ENTER)
    4. join mcache/dcache/cnc/fseq
    5. unprivileged_init
    6. work (tile's loop)
    7. heartbeat/halt loop
    
    
    The ordering is slightly different (Tickoni joins shared memory before sandbox, Firedancer joins after) but functionally equivalent. The key difference is that Firedancer's run callback receives fd_topo_t* and fd_topo_tile_t* pointers, which Tickoni would need to either replicate or wrap.
    
    Verdict: ⚠️ Adaptable but requires bridging. Tickoni would need to: (a) accept fd_topo_t* / fd_topo_tile_t* in its run callback, (b) make those pointers point to valid data, and (c) handle the Firedancer topology structure layout.

Layer 3: The Topology Structure — where it gets ugly
    
    This is the critical part. fd_topo_tile_t contains a massive union of tile-specific configuration (lines 128-1250 of fd_topo.h). Every tile type has its own section — net, shred, replay, pack, execrp, etc. with fields like shred_version, identity_key_path, vote_account_path, accdb_obj_id, etc.
    
    The fd_topo_run_tile() function passes this pointer to callbacks. fd_stem.c reads from it. But here's the thing — Tickoni's tile_process.run() doesn't use this pointer at all. It uses its own LaunchSpec struct (Zig, lines 20-187 of launch_spec.zig) which has:
    
    zig
    pub const LaunchSpec = struct {
        tile_idx: u32,
        tile_id: tile.TileId,
        cpu_placement: cpu_placement.CpuPlacement,
        workspace_name: link.WorkspaceName,
        cnc_gaddr: usize,
        input_link: link.LinkHandles,
        output_link: link.LinkHandles,
        heartbeat_interval_ns: u64,
        event_count: u64,
        policy_limit_cents: i64,
        inject_duplicate: bool,
        inject_malformed: bool,
        crash_after_heartbeats: u32,
    };
    
    
    Verdict: ⚠️ Adaptable with a shim. Tickoni would need a compatibility layer that converts fd_topo_tile_t → LaunchSpec (or vice versa). The Firedancer topology has Solana-specific fields in the union, but those are only accessed by Solana tiles — the harness code itself doesn't read Solana-specific fields.

Layer 4: Shared Memory Access — mcache/dcache/fseq
    
    Tickoni's c_abi bridge already wraps these:
    - tango.c wraps fd_mcache_, fd_dcache_, fd_fseq_, fd_cnc_
    - wksp.c wraps fd_wksp_*
    
    The Firedancer stem uses fd_stem_context_t which has mcache pointers, sequence counters, depth counters, credit availability, and outbound reliable flags. Tickoni's links use the same primitives.
    
    Verdict: ✅ Adaptable. The bridge already exposes the exact same primitives.


Layer 5: The Stem Run Loop
    
    Most Firedancer tiles use stem_run (from fd_stem.c) as their run callback. This is a generic multiplexer template that:
    - Polls input links via mcache
    - Applies credit-based flow control
    - Calls after_frag callbacks
    - Writes to output links via mcache
    - Checks SHOULD_SHUTDOWN at the loop top
    
    This is where Firedancer gets closest to "generic tile harness". But Tickoni tiles don't follow the stem pattern — they have custom loops (e.g., process.zig's RunIngest, RunNormalize loops with consume()/publish() calls, not the stem's multi-link multiplexing).
    
    Verdict: ❌ Not directly compatible. Tickoni tiles don't use the stem loop, and they have different lifecycle semantics (CNC-based halt vs. fseq-based shutdown). Making Tickoni tiles use the stem loop would require rewriting their core execution logic.
    
The Process Model
    
    Firedancer has two modes:
    1. Thread mode (fd_topo_run_thread()): tiles are pthreads in a single process
    2. Process mode (fd_topo_run_single_process() / execve()): tiles are forked children
    
    Tickoni uses a self-exec process model — each tile execve()s the same binary with different arguments. Firedancer's run.c does fork+exec. The mechanisms are different but achieve the same result (process isolation per tile).
    
    Verdict: ⚠️ Adaptable. Tickoni could use Firedancer's fork+exec, or Firedancer's thread mode could run Tickoni tiles in-process.


Critical Objections
    
    Against reusing the harness:
    
    1. The fd_topo_t / fd_topo_tile_t structures are enormous. They're the entire topology config serialized into C structs. The union has Solana-specific fields (shred_version, identity_key_path, vote_account_path, etc.) that would be dead weight. You'd need a parallel topology builder that produces the same layout but with Tickoni-specific fields.
    
    2. The topob.c topology builder has Agave logic. Functions like fd_topob_auto_layout_cpus(topo, cpus, reserve_agave_cores) reserve cores for Agave. Even if you set reserve_agave_cores=0, the layout logic assumes Solana tile kinds.
    
    3. The metrics framework is generated per-Solana-tile. fd_metrics_register() registers per-tile metrics counters that are generated based on tile names. Tickoni would need to either generate its own metrics or bypass the metrics framework entirely.
    
    4. The fd_topo_run_tile() function has hardcoded assumptions. Line 137: if( !tile->allow_shutdown ) FD_LOG_ERR(...). This means the tile must set allow_shutdown in the topology. Line 127: fd_metrics_register(tile->metrics) assumes metrics are allocated. These are small but show the harness isn't designed to be neutral.
    
    5. The fd_stem.c stem loop is opinionated. It expects multi-input, multi-output tiles with credit-based flow control. Tickoni's tiles (especially ingest and audit) are single-input or single-output with different semantics. Forcing them into the stem loop would be like making square pegs round.
    
    6. The sandbox/seccomp setup assumes Firedancer's syscall filter generator. populate_allowed_seccomp() generates BPF filters based on the tile's actual syscall trace. Tickoni would need to either generate these filters or provide permissive ones (which defeats sandboxing).


 For reusing the harness:
    
    1. The c_abi bridge already wraps everything needed. tango.c exposes fd_mcache_, fd_dcache_, fd_fseq_, fd_cnc_. wksp.c wraps workspace ops. sandbox.c wraps sandbox. The bridge is already the thin adapter layer.
    
    2. Firedancer's harness is generic at the structural level. The fd_topo_run_tile_t struct only cares about: (a) footprint/align, (b) init callbacks, (c) run callback, (d) sandbox config. None of these are Solana-specific. The Solana semantics live in the tile implementations (fd_bundle_tile.c, fd_replay_tile.c, etc.), not in the harness.
    
    3. The supervisor process model is already process-isolated. main_pid_namespace() in run.c already forks/execs tiles as separate processes with PID namespace isolation. Tickoni could use this instead of its own self-exec logic.
    
    4. The fd_topo_run_tile() function is the only harness entry point and it's a single function. You can trace its entire lifecycle: join workspaces → privileged_init → sandbox → fill tile → unprivileged_init → run. This is already a minimal, well-defined contract.

Conclusion
    
    Can you make Firedancer believe Tickoni tiles are Firedancer tiles? Yes, partially. The structural contract (fd_topo_run_tile_t, workspace joining, shared memory primitives, sandbox setup) is all generic and already wrapped by Tickoni's c_abi bridge. The challenge is:
    
    The topology builder (fd_topob.c) and the fd_topo_tile_t union are Solana-shaped. You'd need a parallel topology that produces the same C struct layout but with Tickoni fields. This is feasible but non-trivial — you'd be rebuilding fd_topob.c for Tickoni while keeping the Firedancer harness intact.
    
    The stem loop (fd_stem.c) is the wrong abstraction for Tickoni tiles. Tickoni tiles have different execution patterns (single-input pipelines, policy gates, custom loops) that don't fit the stem's multi-input multiplexing model. Forcing them would be worse than writing a separate lifecycle.
    

    My recommendation: Don't reuse the Firedancer harness as-is. Instead:
    1. Use the c_abi bridge for the primitives it already exposes (mcache, dcache, fseq, cnc, wksp, sandbox) — this is the "generic infrastructure" part
    2. Keep Tickoni's own tile_process.zig lifecycle as the tile runner — it's already closer to what Tickoni tiles need
    3. If you want Firedancer process isolation, reuse run.c's fork+exec model but with Tickoni's topology builder (a simpler, finance-oriented version of fd_topob.c)
    4. Don't try to make fd_topo_run_tile() run Tickoni code — the callback signatures match, but the top-level structure (fd_topo_t, fd_topo_tile_t) is a Solana-shaped interface that would require a compatibility shim layer, and the stem loop is the wrong abstraction
    
    The real value of the Firedancer harness is the process isolation and shared-memory infrastructure — which you can access through the c_abi bridge without going through the Firedancer supervisor. The harness itself is Solana-shaped at the topology builder level, and trying to bypass that while keeping the harness is like wearing a Solana costume to look like a Firedancer tile.

    3. The workspace/shmem layer — hugepages are Linux-only
    
    Firedancer's shared memory management (fd_wksp_, fd_shmem_) is built on top of the Linux hugetlbfs filesystem:
    - Mounts /mnt/.fd/.huge (2MiB pages) and /mnt/.fd/.gigantic (1GiB pages)
    - Uses mmap() with MAP_HUGETLB on those mounts
    - Requires sudo and echo N > /sys/kernel/mm/hugepages/ to configure
    
    There is no Windows or macOS equivalent. macOS has MAP_JIT for JIT code but not huge pages in the same way. Windows has CreateFileMapping() with large pages but no shared-memory filesystem overlay like hugetlbfs.
    
    What's actually POSIX and could be portable
    
    A few things could be ported:
    - fork() — works on macOS, not Windows
    - mmap()/munmap()/madvise() — POSIX, not Windows
    - sched_setaffinity() — POSIX, not Windows
    - pipe()/close()/read()/write() — POSIX, not Windows
    - signal()/sigaction() — POSIX, not Windows
    
    But even those only get you to macOS, not Windows. And the core platform (hugetlbfs + seccomp + CLONE_NEWPID) is completely Linux.
    
    Implications for Tickoni's cross-platform goal
    
    You can't reuse the Firedancer harness on macOS or Windows. The harness is not "Linux-agnostic C with optional Linux features." It's deeply Linux — the entire process isolation model (clone + CLONE_NEWPID + seccomp + hugetlbfs) assumes a Linux kernel.
    
    Tickoni's own process model (self-exec per tile via execve in tile_main.zig) has the same fundamental Linux dependency (execve + sched_setaffinity + hugetlbfs). If Tickoni wants to be cross-platform, it needs:
    
    1. Process spawning abstraction: fork() + execve() on Linux/POSIX, CreateProcess() on Windows
    2. CPU affinity abstraction: sched_setaffinity() on POSIX, SetThreadAffinityMask() on Windows
    3. Memory mapping abstraction: mmap() with hugepages on Linux, CreateFileMapping() on Windows, fallback to mmap() without hugepages on macOS
    4. Sandboxing abstraction: seccomp on Linux, no equivalent on macOS/Windows (would need to skip this tier)
    5. PID namespace isolation: No equivalent outside Linux (would need to skip this tier)
    
    The Firedancer harness can't be used on anything but Linux. Tickoni's own process model can't either — it depends on execve, sched_setaffinity, and hugetlbfs. If the cross-platform goal is real, both need platform abstraction layers.

What Firedancer's harness actually gives you
    
    The Firedancer harness at src/disco/topo/fd_topo_run.c is a single function (fd_topo_run_tile) that manages 6 layers:
    
    
    1. launch       → fd_topo_run_tile_t{privileged_init, unprivileged_init, run, ...}
    2. lifecycle    → join wksp → privileged_init → sandbox → fill tile → unprivileged_init → run
    3. topology     → fd_topo_t / fd_topo_tile_t (Solana-shaped)
    4. shared mem   → mcache, dcache, fseq, cnc, fctl (tango primitives)
    5. execution    → stem loop (fd_stem.c) — multi-input multiplexer with callbacks
    6. supervisor   → run.c fork+exec + PID namespace + wait4
    
    
    What we already have wired through c_abi
    
    
    c_abi bridge exposes:
      wksp.*     → fd_wksp_new_named, fd_wksp_attach, fd_wksp_alloc, fd_wksp_free, ...
      tk_mcache_* → fd_mcache_new, fd_mcache_join, fd_mcache_publish, ...
      tk_dcache_* → fd_dcache_new, fd_dcache_join, fd_dcache_app_laddr, ...
      tk_fseq_*   → fd_fseq_new, fd_fseq_join, fd_fseq_query, ...
      tk_cnc_*    → fd_cnc_new, fd_cnc_join, fd_cnc_signal, fd_cnc_heartbeat_query, ...
      sandbox.*   → fd_sandbox_enter (seccomp, caps, UID/GID, PIDNS)
    
    
    That's tango primitives (layer 4) already bridged. The c_abi shim directory (src/tickoni/c_abi/shim/) has thin C wrapper functions over every Firedancer primitive we need:
    
    - tango.c: mcache, dcache, fseq, cnc
    - wksp.c: workspace
    - sandbox.c: sandbox/seccomp
    
    The clean reuse strategy
    
    Think of it like this: [fd harness] calls [a, b, c] → Tickoni rebuilds [tickoni harness] that calls [a, b, c] through the c_abi bridge.
    
    Layer-by-layer breakdown:
    
    Reusable as-is (no changes, just link against)
    
    1. Tango queues — src/tango/{mcache,dcache,fseq,cnc,fctl,tempo}/ are pure Solana-free infrastructure. They're the shared memory primitives. The c_abi shims already expose them. We keep these.
    
    2. Workspace — src/util/wksp/ (workspace alloc/join/detach). We use tk_wksp_* wrappers. The c_abi shim already maps tk_wksp_* → fd_wksp_*.
    
    3. Sandbox/seccomp — src/util/sandbox/fd_sandbox.c is pure Linux syscall stuff. The sandbox.zig module and shim/sandbox.c already bridge it.
    
    4. HTTP server — src/waltz/http/fd_http_server.c is generic HTTP. Not solana. Could be reused for the future tkapi tile.
    
    Reusable with a shim (bridge layer)
    
    5. Tile lifecycle — fd_topo_run_tile() in disco/topo/fd_topo_run.c has a clean contract: take fd_topo_run_tile_t, call the callbacks in order. We already have an equivalent in tile_process.zig. Two options:
       - Keep tile_process.zig as our own tile runner (it's already correct for Tickoni), but reuse the Firedancer function signature for fd_topo_run_tile_t so our callbacks match. That way if we ever want to switch, the interface is the same.
       - Or build a Firedancer → Tickoni bridge: make Tickoni's topology struct convertible to fd_topo_tile_t, pass Tickoni's callbacks into fd_topo_run_tile().
    
    Don't reuse (wrong abstraction for Tickoni)
    
    6. Stem loop — fd_stem.c is a multi-input, credit-based flow-control multiplexer designed for Solana tiles (bundle, shred, replay, pack). It's the wrong model for Tickoni tiles which use single-input pipelines with custom loops. Don't force Tickoni tiles into the stem pattern.
    
    7. Topology builder — fd_topob.c is heavily Solana-shaped (Agave core pinning, reserve_agave_cores, Solana tile kinds). Don't reuse fd_topob.c. Build a parallel, finance-oriented topology builder.
    
    8. Supervisor process model — run.c's main_pid_namespace() with clone(CLONE_NEWPID), wait4(-1, ..., WNOHANG) is Linux-specific and tightly coupled to fdctl. Tickoni's tile_main.zig self-exec model is cleaner. Keep Tickoni's supervisor.
    
    Missing but worth adding to c_abi
    
    9. Metrics — src/disco/metrics/fd_metrics.c is tiny (97B, probably just registration). fd_metrics.h defines the framework. Consider adding tk_metrics_* shims for health monitoring.
    
    10. fctl — fd_fctl.c (flow control) is part of tango infrastructure but not yet in c_abi. Add tk_fctl_* if you need credit-based backpressure in future tiles.
    
    11. tempo — fd_tempo.c (timing/housekeeping) could be added to c_abi for the "no heartbeat during work()" problem described in doc 8. This is how Firedancer keeps the supervisor alive during long processing.
    
    Concrete recommendation
    
    The document 8 already concluded: "Don't reuse the Firedancer harness as-is." I agree with the reasoning but I'd push it further:
    
    Don't try to make Tickoni tiles into Firedancer tiles. Instead, build a reverse bridge — keep tile_process.zig as the canonical runner, and only expose the Firedancer infrastructure primitives through c_abi. Here's the architecture:
    
    
    ┌─────────────────────────────────────────────┐
    │  Tickoni tile_process.zig (our harness)     │
    │  - self-exec supervisor                     │
    │  - join wksp → privileged_init → sandbox    │
    │  - join mcache/dcache/cnc/fseq              │
    │  - unprivileged_init → work loop            │
    │  - heartbeat/halt loop                      │
    └──────────┬──────────────────────────────────┘
               │ calls through c_abi bridge
    ┌──────────┴──────────────────────────────────┐
    │  c_abi bridge (src/tickoni/c_abi/)          │
    │  - wksp.zig + shim/wksp.c  → fd_wksp_*     │
    │  - dcache.zig + shim/tango.c → fd_dcache_*  │
    │  - fseq.zig  + shim/tango.c → fd_fseq_*     │
    │  - cnc.zig   + shim/tango.c → fd_cnc_*      │
    │  - sandbox.zig + shim/sandbox.c → fd_sandbox │
    │                                             │
    │  NEW additions needed:                      │
    │  - fctl.zig    + shim/tango.c → fd_fctl_*   │
    │  - tempo.zig   + shim/util.c  → fd_tempo_*  │
    │  - metrics.zig + shim/tango.c → fd_metrics_*│
    └──────────┬──────────────────────────────────┘
               │ links against
    ┌──────────┴──────────────────────────────────┐
    │  Firedancer infrastructure (unchanged)      │
    │  src/tango/{mcache,dcache,fseq,cnc,fctl,tempo}│
    │  src/util/wksp/{admin,user}                 │
    │  src/util/sandbox                           │
    │  src/waltz/http                             │
    └─────────────────────────────────────────────┘
    
    
    The key insight: Firedancer's infrastructure (tango queues, workspace, sandbox) is the valuable reusable part. Firedancer's harness (stem loop, fdctl, topology builder, supervisor process model) is Solana-shaped and not worth adapting. We already have the right harness (tile_process.zig); we just need to make sure the c_abi bridge exposes every tango/infrastructure primitive Tickoni tiles might need.
    
    The biggest gap today is tempo — adding it to c_abi would solve the heartbeat problem from doc 8 without touching Firedancer harness code.
