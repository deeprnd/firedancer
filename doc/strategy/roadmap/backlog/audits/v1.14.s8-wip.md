    ADR WIP Discussion — What S8 Gets Right and Wrong
    
    The adr_wip.md document evolved through two competing plans:
    
    Phase 1-5 draft (rejected by its own closing analysis): Build Tickoni-owned analogues of Firedancer's topology struct, stem-loop equivalent, tempo/fctl shims. This was flagged as over-engineered — rebuilding what Firedancer already provides.
    
    "Honest assessment" (approved): Thin Tickoni structs embedding the Solana-free subset of Firedancer types, calling the real harness entrypoints directly. This is what S8 implements.
    
    ADR WIP issues that S8 correctly addresses:
    
    1. Registry problem — adr_wip says "the TILES[] pattern IS the registry." S8 T1 builds tile_registry.zig following this pattern. Correct.
    
    2. Multi-link problem — adr_wip says "kill the serialized handoff and adopt topology-driven model." S8 T2 does this. Correct.
    
    3. c_abi expansion — adr_wip lists tempo, fctl, metrics shims. S8 does not explicitly call out tempo/fctl (but the c_abi bridge expansion in audit 8's plan is T5-adjacent). Gap: S8 doesn't explicitly mention adding tempo/fctl to c_abi.
    
    4. Sandbox — adr_wip says sandbox is Solana-free and already wrapped. S8 T5 wires SandboxConfig into the harness entry point. Correct.
    
    ADR WIP issues that S8 misreads or under-specifies:
    
    1. Parent-side supervisor reuse (T7) — The audit investigation found Firedancer's run.c path is "tightly coupled to fdctl, fd_topo_t, PID namespace, clone()." S8 correctly scopes this as "attempt and document" rather than "guaranteed rewrite." However, S8 T7's investigation target is broader than it needs to be: it says investigate "run.c/run1.c/fd_boot.c conventions for spawn/crash reporting." But the key question is narrower: can Tickoni's self-exec child tracking (waitProcess) be replaced by Firedancer's wait4+pipefd model without importing fdctl? The story should name the exact coupling points to check (fdctl's TILES[] array, fdctl's topo file loader, clone(CLONE_NEWPID) in run.c).
    
    2. The "call fd_topo_run_tile" decision — S8 T4 says "migrate... to a real fd_topo_run_tile call." But adr_wip's honest assessment shows fd_topo_run_tile takes fd_topo_t* and fd_topo_tile_t* — Solana-shaped structures with fields like tile_kind, kind_id, is_agave. The thin embedding approach (Tickoni struct embedding fd_topo_t's Solana-free fields) is correct in theory, but has a serious practical risk: if fd_topo_run_tile reads ANY Solana field during its execution (not just passes them around), the Thin Embedding fails. S8's acceptance criteria check that product code doesn't import these types, but doesn't check that fd_topo_run_tile doesn't silently read them. This is a pre-implementation validation gate that should be explicit in the story.
    
    3. Scope creep risk — S8 has 10 tasks (T1-T10) covering registry, links, c_abi bridge, lifecycle migration, sandbox/seccomp, stuck-tile defense, parent-path investigation, engine drift guard, docs update, and evidence. The story notes this "may be too large for one story" and suggests splitting. This is correct. The tasks naturally break into 3-4 independent chunks. S8 as stated risks being the story that never ships because it's 800+ lines of scope.
    
    4. Seccomp policy generation — S8 T5 mentions contrib/codegen/generate_filters.py. This tool generates seccomp-BPF filters for Firedancer tiles by tracing their syscalls. The question is whether it can do this for Tickoni tiles without requiring Firedancer's topology/config context. S8 doesn't investigate this dependency. Gap.
    
    5. What stays Tickoni-owned — S8 is explicit about what doesn't get reused (stem loop, topology builder, fdctl coupling, PID namespace). But it should also be explicit about what stays: tile_process.zig's self-exec boot/heartbeat/halt loop, supervisor.zig's child tracking. The "honest assessment" in adr_wip says "no supervisor rewrite," but S8 T4 says "migrate lifecycle to fd_topo_run_tile" which IS effectively a lifecycle rewrite. This tension needs resolution before implementation starts.

    Does S8 follow firedancer-orchestration-reuse.md?
    
    Mostly yes, with one structural tension. S8 correctly:
    - Rejects stem loop reuse (right for Tickoni's single-input tiles)
    - Rejects topology builder reuse (right — fd_topob.c is Solana-shaped)
    - Rejects full Firedancer harness reuse (correct — per Option 3)
    - Plans a thin adapter approach (aligned with Option 3)
    
    The tension: S8 says "migrate tile_process.zig to fd_topo_run_tile" which would make tile_process.zig (currently product code) become the adapter layer. If it works, fine. But if fd_topo_run_tile silently reads Solana fields, the whole approach fails. S8 needs a pre-implementation gate: "Verify fd_topo_run_tile doesn't read tile_kind/kind_id/is_agave during execution."
    
    Does S8 follow tile-orchestration.md?
    
    Yes. Strongly aligned. The registry, link arrays, bootstrap separation, lifecycle ordering, health semantics, crash visibility, and drift guard all match tile-orchestration.md's requirements.
    
    Critical risks before implementation starts:
    
    1. Can fd_topo_run_tile actually be called from Tickoni without dragging in fd_topob.c or fdctl? This is the make-or-break question. The story assumes the answer is "yes, with a thin embedding." It needs proof.
    2. Scope is too large for one story. 10 tasks spanning registry, links, c_abi expansion, lifecycle migration, sandbox/seccomp, stuck-tile detection, parent-path investigation, engine drift gate, docs, and evidence. S8 itself acknowledges this. Split into 3-4 stories before implementation.
    3. tempo/fctl shims are not explicitly scoped in S8. Audit 8's plan requires them for proper stuck-tile defense. S8 mentions "supervisor-side heartbeat-staleness detection" but doesn't say how tiles will get the timing primitives to emit heartbeats inside their work loops without polling.
    4. Seccomp generation dependency unknown. generate_filters.py may require Firedancer topology context. S8 doesn't validate this.
    5. The v14.s8 commit only wrote docs. The status field in v1.14.md still says "Backlog" for S8. The justfile has no engine-check-changes recipe. This is consistent with "planning stage" but worth flagging that the commit was misnamed — it documented S8 but didn't implement it.
