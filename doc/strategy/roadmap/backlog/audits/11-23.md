Analysis: C. LaunchSpec / link cardinality (issues 11 & 23)

    Finding 11: LaunchSpec has exactly one input_link/output_link — not N

    What the code says (launch_spec.zig:33-36):


    input_link: link.LinkHandles = .{},
    output_link: link.LinkHandles = .{},


    LinkHandles is a POD struct representing exactly ONE channel (one mcache/dcache/fseq triplet). One gaddr pair, one depth, one MTU. This is a 1:1 cardinality by design.

    Why this matters: A tile in a real topology can have multiple inputs (fan-in) or multiple outputs (fan-out). For example:
    - tkaudt might receive events from both tkings AND tkpoly (source events + policy decisions)
    - tkdisp might fan out to multiple agent workers

    The current model has no way to express "tile N receives from channels A, B, and C." It can only carry one.

    The latent failure: Currently all payment topologies are linear chains (tkings -> tknorm -> tkdedu -> tkpoly -> tkaudt). Each tile has exactly one input and one output. So the single-link model "works" today. But adding fan-in/fan-out would silently lose all but one link.

    What fixing 11 requires: A decision on the multi-link contract. Options:

    1. Array-based: input_links: [N]LinkHandles — but N is topology-dependent, and Zig needs compile-time constants or heap allocation. Not embeddable in a fixed-size spec file.
    2. Count + fixed buffer: input_count: u4, input_links: [16]LinkHandles — fixed max, wastes space for most tiles, but fits in a fixed-size struct for the spec file round-trip.
    3. Separate link table: The spec carries a link table index (N links), and a sidecar file/array holds the actual handles.
    4. Erase multi-link from LaunchSpec entirely: Keep LaunchSpec as a single-handoff record. Build links at bootstrap time in tile_process.zig from the topology file, not from LaunchSpec fields.

    Option 4 is the cleanest if the topology file already encodes all link relationships. LaunchSpec then becomes purely "tile identity + runtime bootstrap params." But this changes how tiles discover their links.



    Finding 23: supervisor.zig's channel-selection loop is genuinely last-match-wins

    The code (supervisor.zig:250-258):
    zig
        for (self.topo.channels, 0..) |ch, ci| {
            if (ch.dst_idx == i) input_link = link_handles[ci];
            if (ch.src_idx == i) output_link = link_handles[ci];
        }


        This iterates ALL channels for each tile. If tile 4 has two input channels (say, channels 1 and 2), the loop:
        1. Iteration 1: ch.dst_idx == 4? No. Skip.
        2. Iteration 2: ch.dst_idx == 4? Yes. input_link = link_handles[1]
        3. Iteration 3: ch.dst_idx == 4? Yes. input_link = link_handles[2] — overwrites #2
        4. Iteration 4: ...

        Channel 1 is silently dropped. The last matching channel wins.

        This is not a theoretical problem. It's latent because the payment topology is linear. But any future topology with fan-in will break without anyone noticing. The tile will simply never see half its inputs.

        What fixing 23 requires: A sidecar payload split. The channel-selection logic in the supervisor needs to:
        1. Count how many input/output channels a tile actually has
        2. Either error out if the count exceeds LaunchSpec's capacity, OR
        3. Switch to the multi-link model (see fixing 11)

        The sidecar split would look like: the supervisor iterates channels, collects all matching handles into a temporary buffer, counts them, then either (a) passes them as an array if the LaunchSpec supports it, or (b) errors if the tile has more links than the spec can carry.



        Cross-cutting issue: Payment-specific fields in LaunchSpec

        The fields (launch_spec.zig:47-50):

        zig
        event_count: u64 = 0,
        policy_limit_cents: i64 = 0,
        inject_duplicate: bool = false,
        inject_malformed: bool = false,


        And in the init parameters (lines 63-66), plus the config struct ProcessPipelineConfig (supervisor.zig:30-36) which mirrors these.

Why this is wrong: LaunchSpec is the generic runtime handoff from supervisor to tile process. It's a fixed-size binary record that survives across tile processes via the file system. It should carry only runtime bootstrap information:
    - Tile identity (tile_idx, tile_id)
    - CPU placement
    - Workspace/shmem connectivity (workspace_name, cnc_gaddr)
    - Link handles (input/output — the generic part)
    - Operational params (heartbeat_interval_ns, crash_after_heartbeats)

    event_count, policy_limit_cents, inject_duplicate, and inject_malformed are payment pipeline test configuration. They belong in PaymentPipelineConfig or ProcessPipelineConfig, not in the generic tile launch spec.

    The reason they ended up here: to keep thread-mode and process-mode test behavior byte-identical, the payment config fields were pushed through LaunchSpec so the tile child process could read them from the same place. But this pollutes a generic struct with domain-specific test parameters.

    What a sidecar payload split would look like:


    LaunchSpec (generic, fixed-size, tile-independent):
      magic, version, tile_idx, tile_id, cpu_placement
      workspace_name, cnc_gaddr
      input_link, output_link  (or link_tables)
      shmem_path, heartbeat_interval_ns, crash_after_heartbeats

    ProcessConfig (domain-specific, variable shape, process-mode only):
      event_count, policy_limit_cents
      inject_duplicate, inject_malformed
      (other pipeline test config)


    The supervisor writes both files. The tile reads LaunchSpec from --shmem-path/tile_N.spec and reads ProcessConfig from a separate path or command-line flag. Or, if the tile always runs through __tile-run, the launcher passes ProcessConfig as additional argv/env.

Firedancer's model: topology carries multi-link; no "LaunchSpec" exists

    Firedancer doesn't have anything like Tickoni's LaunchSpec. Their tile handoff is fd_topo_run_tile(topo, tile, ...) — the supervisor passes the full topology pointer and a tile pointer into the run function. The tile reads everything it needs from the topology struct. There's no self-exec, no file-based bootstrap, no serialized handoff record.

    How Firedancer handles 1-N / M-N fan-in/fan-out

    fd_topo_tile_t has fixed-size arrays for links (fd_topo.h:137-145):

    c
    ulong in_cnt;
    ulong in_link_id[ FD_TOPO_MAX_TILE_IN_LINKS ];       // up to 128 inputs
    int   in_link_reliable[ FD_TOPO_MAX_TILE_IN_LINKS ]; // per-link reliability
    int   in_link_poll[     FD_TOPO_MAX_TILE_IN_LINKS ]; // per-link polling flag

    ulong out_cnt;
    ulong out_link_id[ FD_TOPO_MAX_TILE_OUT_LINKS ];     // up to 32 outputs


    MAX_IN = 128, MAX_OUT = 32. These are compile-time constants. A tile can have 0 inputs (source tile like pack), 0 outputs (sink tile like gui), 1 (typical pipeline), or many (fan-in/fan-out).

    The topology has FD_TOPO_MAX_LINKS = 256 total links across the entire system.

    How Firedancer resolves links at runtime

    In fd_stem.c:762-837, the stem run() function (the actual tile loop) does this:

    c
    const fd_frag_meta_t * in_mcache[ FD_TOPO_MAX_LINKS ];
    for( ulong i=0UL; i<tile->in_cnt; i++ ) {
        if( !tile->in_link_poll[ i ] ) continue;
        in_mcache[ polled_in_cnt ] = topo->links[ tile->in_link_id[ i ] ].mcache;
        polled_in_cnt += 1;
    }

    fd_frag_meta_t * out_mcache[ FD_TOPO_MAX_LINKS ];
    for( ulong i=0UL; i<tile->out_cnt; i++ ) {
        out_mcache[ i ] = topo->links[ tile->out_link_id[ i ] ].mcache;
    }


    Key point: the topology is the source of truth. tile->in_link_id[0] is a link ID (an index into topo->links[]). The stem resolves it to the actual mcache pointer at boot time, passing arrays of counts and pointers to stem_run().

    How Firedancer polls multiple inputs

    The stem loop is a multi-input multiplexer (fd_stem.c:390-756). Every iteration:

    1. Checks SHOULD_SHUTDOWN
    2. Does housekeeping (metrics, flow control credits)
    3. Calls before_credit callback
    4. Polls inputs in randomized round-robin order to avoid lighthouse effects
    5. Calls during_frag / after_frag callbacks
    6. Publishes to outputs via fd_stem_publish()

    The polling order is shuffled periodically (lines 500-506):

    c
    ulong swap_idx = fd_rng_uint_roll( rng, (uint)in_cnt );
    fd_stem_tile_in_t in_tmp = in[ swap_idx ];
    in[ swap_idx ] = in[ 0 ];
    in[ 0 ] = in_tmp;


    This is where Tickoni's audit finding "last-match-wins" would explode — Firedancer has 3 layers of defense:

    1. Topology declares it: fd_topo_tile_t has in_cnt + arrays, not single fields
    2. Stem handles it: the run loop explicitly iterates in_cnt inputs
    3. No silent truncation: if a tile declares 3 inputs, stem reads all 3

    How Firedancer handles process isolation

    Firedancer has two modes:
    - Thread mode (run_tile_thread): creates pthreads with pthread_create(), passes topo/tile pointers via args struct
    - Process mode (run.c:run1.c): forks via clone(CLONE_NEWPID), each child gets a fd_topo_tile_t* into the shared topology

    Neither uses a "LaunchSpec" file. The supervisor maintains the topology in shared memory throughout the tile lifecycle.

    How Firedancer handles metrics (avoiding Tickoni's snapshot problem)

    Firedancer doesn't do string-matched metric snapshots. From the audit findings (7-20-24.md):

    > Firedancer reads metrics from a shared memory array indexed by position. The supervisor never does string comparison to find metrics.

    Each tile has a position in topo->tiles[]. The topology has topo->tiles[tile_idx].metrics which is a pre-allocated shared memory block for that tile's metrics. The supervisor (run.c) identifies tiles by position when they crash (child_names[i] copied from tile->name at spawn time). Metrics are accessed via topo->tiles[tile_idx].metrics — position-indexed, never string-matched.



    What this means for Tickoni

    The Firedancer comparison clarifies the right direction:

    Firedancer puts link information in the topology, not in a handoff record. The topology struct owns the graph: which tiles connect to which links, and which links feed each tile. Tiles read their link info from the topology at boot time. There is no separate "bootstrap file" that needs to carry link handles.

    Tickoni's problem is that it's trying to pass link information through a serialized file (LaunchSpec) meant for simple bootstrap. That's the wrong abstraction.

    What Firedancer does differently that's instructive for Tickoni:

    1. Topology is the graph. fd_topo_tile_t has in_link_id[] + in_cnt arrays. No "last-match-wins" because the topology declares the cardinality explicitly.

    2. Stem multiplexes at runtime. The stem loop gets in_cnt + in_mcache[] as arrays. It iterates all inputs. Tickoni's tiles don't use the stem, but they could build the same pattern: the supervisor resolves all input/output channels for each tile into arrays and passes them to the tile, rather than serializing one link into LaunchSpec.

    3. No hybrid payload. Firedancer doesn't mix generic runtime bootstrap with domain-specific test config in the same record. Tile lifecycle and test parameters are separate concerns.

    4. Position-indexed everything. Tile identity → topology position → metrics block. No string matching anywhere.

    Recommended direction for Tickoni (informed by Firedancer):

    The sidecar split the audit recommends is right, but the full picture is:

    - Topology file carries the graph: link definitions, tile→link mappings, fan-in/fan-out cardinality
    - LaunchSpec carries tile identity and bootstrap params only (tile_id, workspace, cnc, shmem path, heartbeat)
    - Supervisor resolves channels for each tile from the topology at startup, builds per-tile link handle arrays, passes them to tiles via an init call or environment — not via LaunchSpec
    - Tile processes receive link handles through whatever bootstrap mechanism is cleanest (init callback, argv, or a second bootstrap file), then iterate all of them

    This matches Firedancer's pattern: topology owns the graph, bootstrap owns identity, the tile runs the loop.
